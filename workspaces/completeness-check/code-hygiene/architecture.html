Completeness Check Code Hygiene: how a CC review is produced and shown, and where to clean it up

Bureau checklist files, the CC runbook and cityhall cooperate to show one completeness-check comment. The item's identity lives in a JSON string, the group is a slugified heading, the title is written by an agent, and every comment is stored twice. This page maps how it works and where it should end up.

The goals

Six goals, in the order the slices land them (§1.1).

  1. An item is a row you can join on. The checklist item id sits in a typed column, and nothing parses JSON to find it.
  2. Presentation is data, not output. Title, group, order and number come from the checklist the review ran against, resolved when the page is read; released reviews too, on the verdict-override precedent (P6). renumbering is a MINOR bump, so numbers never move inside a MINOR (P2)
  3. One copy of each comment. The review row describes the review; the comment rows describe the comments.
  4. One read model. Landing, panel, sheets, search and the PDF read a CC review through one adapter.
  5. Only formats still produced, plus a frozen path for archived ones.
  6. Bifurcated UIs, shared skeleton. Formal review and CC keep their pages; the pieces that are the same are the same code.

This is not a build plan. Each slice below becomes a feature spec that adds itself to this page's Amended-by line.
