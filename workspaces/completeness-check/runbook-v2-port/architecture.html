COMPLETENESS CHECK · RUNBOOK V2 PORT

Completeness Check → Runbook v2

A feature-parity port of the legacy completeness-check workflow to a conductor2 runbook. The port keeps the same steps, the same files and the same review rows. It adds a database run row, a checkpoint per step, a reviewFiles subset input, and opt-in persistence of each step's output to Storage. Companion to DESIGN-SPEC.md.

OverviewWhat changes

Today a completeness check runs on the legacy TypeScript runner. Nothing on the run control plane can see it, and its files reach Storage only when the run ends. After the port, conductor2 runs the same steps, every step leaves a checkpoint, and each step's new files can be uploaded as soon as the step finishes.

Inputs & publishThe request, the subset, the publish

The run's inputs are one zod-validated request.json. Arrays are allowed, so reviewFiles is a real list rather than a comma-separated string. Model choices moved out of the request and into runner presets.

Step persistenceKeep every finished step in Storage

An expensive review fan-out followed by a crash in a cheap late step shouldn't lose anything. conductor2 can now upload a step's new files as soon as its contract passes. The feature is off by default, filterable, and never allowed to fail the run.

bureau/runbooks/completeness-check/runbook.yamlpersist: steps: all # all | [step ids]; no block = off skip: [1.2-stage-submission, 1.3-facts] # DB data pulled into the run, never uploaded rules: # optional step-id globs → path filters "2.1-review/*": { exclude: ["**/*.tmp"] } # one-run override: CONDUCTOR_PERSIST=off | on

TestingIterate against the legacy reviews already on file

Nothing legacy is re-run. Each v2 run, on any guide subset, is compared with two existing legacy reviews of the same submission. Items where all three agree are accepted for free. Only disagreements reach an adjudicating agent, and its verdicts build up an answer key so later loops don't pay for them again.

Tier 0 · contracts

npm test runs every step contract over the curated example lamar-v4-cc1-cc21. No run, no tokens.

Tier 1 · self-replay

conductor stage 2.2 --scenario …, then advance through 2.10 with publish:false. The curated 2.1 output must reproduce the curated review-comments.json. It catches wiring regressions while bugs are being fixed.

Tier 2 · the compare loop

Baseline: A = Opus 5 review 41a49412, B = Sonnet 5.5 review 196de05b (D28). compare.ts filters A and B to the v2 run's guides and sorts each item into agree / keyed / unresolved / guide-drift / forced. It reads A and B from review_comments, and the loop runs at runs=1 like both baselines. Adjudicate one Opus cell per guide with unresolved items, under blind labels. Scorecard merges verdicts into the answer key and reports per guide, with cause tags (D29).

Unit tests

conductor2: config (including logs), globs, dedupe, never-fail (mock server). cityhall-new: route validation, the 200 cap, too_large, admission. bureau: lane B flags, resolve, grouping injection, the table-only id parser, 2.11 over a recorded stream, compare.ts.

One loop

all three runs (A, B, v2) give the item the same status?yes →accepted, no tokens
no ↓
guide text changed since A and B ran?yes →guide-drift, reported, not scored

no ↓
otherwise→blind Opus adjudication: correct status, which runs were right, cause tag; merged into the key

Claim (D29): after the first loops warm the answer key, a re-run after a bug fix costs adjudication tokens only for disagreements nobody has judged yet.
