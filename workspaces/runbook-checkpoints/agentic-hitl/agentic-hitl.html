RUNBOOK CHECKPOINTS · AGENTIC HITL

Agentic HITL — who writes the question, who writes the answer, and where the schema isn't

A gate is a step that runs nothing. The agency at a gate belongs to the driver, not to the step — and on one of the two lanes there is no agent at all. Companion to DESIGN-SPEC.md.

Draft v1 · 2026-09-18 · as-built, verified against code + prod · click a tab ↓

Section 1A gate is a step that runs nothing

The natural assumption — an agent reads the gate, reasons about it, and emits a decision matching a schema it was handed — is wrong in three separate ways. Start with the step itself.

bureau/runbooks/smoke/steps/2.3-hitl/step.yamldesc: 'HITL (eng, optional): does the digest read true to the briefs?' runner: none readout: 2.2-digest/digest.md inputs: - 2.2-digest outputs: - decision.json - decision.md

runner: none means no harness is launched, no model is called, no tokens are spent. The step's contract simply fails until the declared outputs exist on disk, and conductor advance exits 75 for the whole pass. The gate is a hole in the graph that something outside the graph must fill.

the correction No agent runs at a gate. Whatever agency exists belongs to the driver — the session or the loop that notices the 75 and goes to find a person. And the driver is an agent on only one of the two lanes.

Section 2The agent's three roles at a gate

There is an agent here — the captain: the /conductor Claude Code session driving a local run. None of its three roles involves the schema.

A · Produce the readout upstream step agent

The gate's readout: points at another step's artifact — 2.2-digest/digest.md, written by an ordinary agent step.

This is the only agent-authored content on the card, and it is prose. Nothing types it, nothing validates it against the gate.

B · Publish the question captain session

Reads: advance stdout (parked step id + readout path) · the readout file · adjudication.md · the step's contract.test.ts · $RUN/runbook-run-id.txt

Writes: one shell call. The only thing it authors is --prompt.

the captain's entire authorship at a gate · conductor SKILL.md §6QID=$($HITL ask --run-id $RUNBOOK_RUN_ID --gate 2.3-hitl --kind decision \ --prompt "<what the gate is asking, in one line>" \ --readout $RUN/2.2-digest/digest.md) ▲ └── free text. The agent writes this sentence and nothing else.

Everything else on the card is structural: kind from a flag, readout_storage_path from an upload, allow_report_back from a flag (_build_payload, runbook_hitl_cli.py:76). The CLI has a --schema-file flag (:230) — and nothing in any repo passes it.

C · Decide it itself — but only when licensed captain session

A run's request.json may carry directives.decide: string[] — waiting-step ids the driver may close without a human (the Request zod in smoke/steps/1.1-inputs/contract.test.ts). When the parked step is named there and its folder holds written criteria, the captain decides against adjudication.md, records the answer with --decided-by naming the session, and cites the directive. Otherwise it publishes and blocks on await-answer.

No code reads directives.decide. It is honored entirely by agent instruction-following (SKILL.md §5). See Q4.

XWhat the agent never does

Author, choose, generate, validate against, or even read decision.schema.json. The captain learns the answer's shape the way a human would — from adjudication.md prose and the zod it can read in contract.test.ts. The schema file is invisible to it. There is no "agent schema" to reconcile with the DB schema; there are only hand-maintained duplicates.

the asymmetry Compare the two lane headers. The local lane's first column is an agent; the cloud lane has no agent column at all. The two lanes register gates through entirely different code paths — and only the cloud one knows decision.schema.json exists.

Section 5Where the schema is, and why it is almost never there

schema_for (callback.rs:141) reads decision.schema.json beside the step's step.yaml and ships it verbatim. It is reached from exactly one place — gates_for, in the EXIT_WAITING arm of an advance pass — and the callback only fires when both a URL and a run id are present:

conductor2/src/verbs.rs:2554 — the whole gateif let (Some(url), Some(id)) = (callback, run_id) { crate::callback::send(url, id, *reported, cost, &gates, seat.as_ref()); }

--callback is a cloud-lane flag. A local run never sends it, so schema_for is never called, and the gate row's schema is whatever ask put there — null, because nothing passes --schema-file.

Section 6What the as-built justifies cutting

Ordered by what the evidence supports, not by ambition. Nothing here argues for generating schemas from the agent, because no agent is near them.

1 · decided_by from the sessionSHIPPED→ 2 · retire `choice`next→ 3 · close the local-lane gapmakes 4 observable→ 4 · pick a floorkeep or delete the schema

1 · decided_by from the session — shipped

substation#265 + cityhall#678. The field was stated twice (the column and the decision object) and fed from the session only once, which is the only reason the console demanded a signed-in human type their own name.

2 · Retire the choice vocabulary

Have the console post status directly; #4 and #5 collapse to {schema_version: 1, ...answer} and stop being translators. Two of the six statements become one line each.

3 · Close the local-lane gap before judging the schema

Either teach the local path to read decision.schema.json (pass --schema-file, or move the read into ask), or delete schema_for and the ajv arm. Today the column is dead weight that looks live.

4 · Then pick a floor

With the gap closed, one calibration run makes the choice observable rather than theoretical: either the per-step schema earns its keep, or contract.test.ts becomes the single definition and #2 is deleted outright.

QOpen questions

  • Q1 — Is schema a validation contract (ajv at the door) or a rendering contract (generate the form)? It is declared as the first and used as neither. If rendering is the goal, payload already exists for render content and the two should not both be structural.
  • Q2 — Should ask read decision.schema.json itself rather than taking --schema-file? The path is derivable from the gate id, so the flag pushes a decision onto an agent with no reason to make it.
  • Q3 — gate_kind classifies by declared output filenames (callback.rs:120), so 1.1-inputs (outputs request.json) would report as an operator gate. Harmless today because it is satisfied before the first advance — but is filename-inference the right classifier, or should step.yaml declare a gate: key?
  • Q4 — directives.decide is honored entirely by agent instruction-following; no code reads it. Should conductor enforce it, or is prose the right level for a license only an agent can exercise?
  • Q5 — The cloud lane has no captain, so there is no directives.decide path there at all. Is agent self-decision meant to be local-only?
