Section 1Two lanes, one shared data contract

Every runbook run gets a durable runbook_run row, an ordered runbook_checkpoint stream, and — when it parks at a gate — a runbook_hitl_question. The tables are identical across lanes; only who writes them and how an answer gets back into the run differ.

LLocal lane

1.0 and 2.0 runbooks, run in a local Podman container driven by a live /conductor captain session.

  • Captain shells out to app_client.py to write the run / checkpoints / questions.
  • Answerable in-session (chat) OR in the UI.
  • Captain polls the question row, writes decision.json locally, resumes.
  • Multi-turn is free: the live captain answers clarifications from context.

CCloud lane

2.0 runbooks only, run in a per-project Vercel Sandbox driven by the substation runbook/run launcher.

  • Launcher writes the run / checkpoints / questions.
  • Answerable in the UI only (no captain).
  • Sandbox is stopped while parked → answer returns via an Inngest resume event; the launcher writes decision.json.
  • Multi-turn via an out-of-band conductor run-step clarifier — zero conductor2 change.

Section 5Question lifecycle & the human-input supertype

A gate accepts a supertype of human input. Only a decision projects to decision.json and advances the graph; a clarification is answered by an agent but never satisfies the gate.
