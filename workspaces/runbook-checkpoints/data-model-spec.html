Section 1Two lanes, one shared data contract

Every runbook run gets a durable runbook_run row, an ordered runbook_checkpoint stream, and — when it parks at a gate — a runbook_hitl_question. The tables are identical across lanes; only who writes them and how an answer gets back into the run differ.

LLocal lane

1.0 and 2.0 runbooks, run in a local Podman container driven by a live /conductor captain session.

  • Captain shells out to app_client.py to write the run / checkpoints / questions.
  • Answerable in-session (chat) OR in the UI.
  • Captain polls the question row, writes decision.json locally, resumes.
  • Multi-turn is free: the live captain answers clarifications from context.

CCloud lane

2.0 runbooks only, run in a persistent per-project Vercel Sandbox driven by the substation launch route + reconcile cron — no Inngest (v2).

  • The launch / callback / reconcile routes write the run / checkpoints / questions, reading the run dir structurally.
  • Answerable in the UI only (no captain).
  • Advance runs detached (outlives the request; no 800s cap). Sandbox is stopped while parked → the answer route writes the gate row and fires a detached resume (reconcile backstops); the resume writes decision.json.
  • Multi-turn via an out-of-band conductor run-step clarifier — zero conductor2 change.

Section 5The four control-plane routes — how the DB row moves

Three of them — launch, callback, reconcile — are the unbuilt control plane (Phase 2; they depend on Jason's detached-sandbox API). The answer / decide route ships in substation#245. the mental model The DB row is the whole state; four triggers move it — a human start (launch), the run reporting back (callback), a human answer (decide), and a timer that repairs anything the first three dropped (reconcile). The hot fires inside launch & decide are pure latency wins; reconcile guarantees forward progress even if every hot fire is lost. The claimed_at lease + a row-level lock stop a cron tick and a hot fire from double-advancing one run dir.
These three routes replace substation/src/inngest/functions/runbook-run.ts; they depend on Jason's persistent-sandbox detached-command API (out of scope here — spec §1.3/§5). Their DB-write halves already exist in substation/src/lib/runbook-run.ts (createRunbookRun / updateRunbookRun / postCheckpoint / createHitlQuestion). Detail in DESIGN-SPEC.md §5 + D51/D52.
