## Problem

A sir run gets its clerk documents from county websites, and those sites put up walls an agent cannot pass: an account it has to create, a login it does not hold, a CAPTCHA a solve could not clear. On the local lane this is solved and ordinary. The acquire step leaves its **headed Chrome open at the page**, writes what it needs a person to do, and a person at the machine does it (`bureau/runbooks/site-research/steps/9.8-acquire/prompt.md:14`, "leave your headed browser session open at that page … what he does at the page it is sitting on"); the `9.7-hands` gate parks the run until `hands-done.json` says each item was done or declined (`9.7-hands/contract.test.ts:27-38`).

On the cloud lane the same run cannot do this at all, and the reasons are four separate gaps, each verified 2026-09-24:

1. **There is no browser to leave open.** A Vercel sandbox has no display. A cloud step rents a browser from Browser Use Cloud through `noetic-browser` (`conductor2/containers/bin/noetic-browser`, at `/usr/local/bin` in the image), which creates it, binds an `agent-browser` session to its CDP URL, and records `{id, cdp_url, live_url, …}` in the step's `scratch/browser.json` (`:126-127`). That browser runs on the vendor's machines, not in the sandbox — but **conductor stops it on every step exit**: `browser::reap` runs after every agent attempt and every script step (`conductor2/src/verbs/agent.rs:263`, `:987`), and reap is `stop --all` over the record (`noetic-browser:265-274`). The step that hit the wall ends when it parks, and its browser dies with it.

2. **Nothing puts the live view on the card.** The vocabulary exists end to end: the CLI takes `ask --live-view-url` for a `hands` question and puts it in the payload (`bureau/runbooks/lib/runbook_hitl_cli.py:637`, `:343`); `runbook_hitl_questions` has a `live_view_url` column and a `hands` kind (`substation/supabase/migrations/20260908000000_run_control_plane.sql:95,:116`); the console's hands card renders "Open live browser view ↗" with the credential warning and a **Mark done** button (`cityhall/src/lib/runbook-runs/RunbookHITLQuestion.svelte:75`, `:383-407`, origin/main). But no producer fills it. The cloud captain's `ask` has no live-view parameter (`bureau/runbooks/lib/captain.py:190-192`) and passes none at park (`:531-538`); conductor's callback `Gate` carries no such field (`conductor2/src/callback.rs:58-88`). Prod (`mgxqsrjutswbciyrltwd`, all time): **77 `decision` rows, 2 `operator`, 0 `hands`, 0 with a live URL.**

3. **A cloud `hands` answer lands in the wrong file.** The reconcile loop writes every decided gate's answer to `<step>/decision.json` and `decision.md` (`substation/src/lib/reconcile-loop.ts:438-456`, `plan.ts:625-631`, origin/main). The hands gate's contract reads `hands-done.json` (`9.7-hands/contract.test.ts:38`). The decide controller accepts a schema-less `hands` answer precisely so a person can close one (`decide-controller.ts:148-150`), and then the file it produces satisfies nothing. A cloud run that reaches `9.7-hands` with items parks forever.

4. **Until this week, a chain of gates was asked all at once.** Conductor listed every `runner: none` step whose contract fails as open at exit 75, reached or not; smoke run `7c2561b4` (2026-09-24) opened four cards on its first park, three about an animal nothing had drawn. Fixed in conductor2#114: a gate is open only once its inputs are in. This spec assumes it.

What the local lane has and the cloud lane lacks is one thing: **a browser a person can act in, that the next step can pick back up.**

## 1. The shape of a handoff

A handoff is a gate, not a mid-step pause (D1). The step that hits the wall finishes, a `runner: none` gate parks the run, and the step that continues the work starts as a fresh session that reads the run directory. Site-research already has this shape (`9.8-acquire` → `9.7-hands` → `9.8-acquire` again, reading `hands-done.json`). The cloud lane adds one thing: **substation can put a hosted browser in front of the person at any time, and tell the resumed step which one they used.**

The walk, for a cloud sir run that needs an account on a clerk site:

1. **The acquire step** opens a hosted browser (`noetic-browser open`), navigates to the portal, and meets the account wall.
2. It writes the hands item (`needs-hands.json` + `needs-hands.md`: portal, document, the **page URL** it is on, what the person does there, and the **name of the browser** it was using), **holds** that browser for the reuse window (`noetic-browser hold --seconds 1800`), and exits. Its contract passes; the item is recorded, not resolved. Two items on two portals mean two browsers, each held by name (D6).
3. **The hands gate** parks the run (exit 75). Conductor's callback reads each item's page URL and held browser (id, live URL, CDP URL, vendor expiry, hold expiry, proxy flag) from the run directory and ships them on the gate (D5). Substation stores them as the question's **browser pointers**, one per item (D11). The sandbox stops and snapshots. The held browser keeps running at the vendor for now: disconnecting CDP does not stop a Browser Use browser ([concepts/browser](https://docs.browser-use.com/concepts/browser)).
4. **The person** opens the card. Each item has its own embed and **Open browser** button. The button calls substation's open-browser route (D2): inside the reuse window and still `active`, it returns the held browser's live view, logged-in state and all; otherwise it stops the old one, **creates a fresh browser** with the vendor's full 240-minute timeout and the same proxy setting, **navigates it to the item's page URL over CDP**, stores the new pointer, and returns its live view. The route is idempotent per item — a second click, or a second person, gets the same browser. The live view is interactive and embeds in an iframe ([cloud/browser/live-preview](https://docs.browser-use.com/cloud/browser/live-preview)).
5. The person logs in and marks the item **done** (or **declined**, D7). Done closes that item's embed and button (D9); the other items' browsers stay open until they are answered.
6. **Substation** writes `hands-done.json` into the gate's folder — one `{document, outcome, note, browser: {id, cdp_url}}` row per item — and resumes the sandbox from its snapshot.
7. **The acquire step runs again** as a fresh session, reads `hands-done.json`, and for each done item **attaches** to the named browser (`noetic-browser attach --id …`, which re-binds an `agent-browser` session to its CDP URL and records it in the step's own `scratch/browser.json`). It is inside the person's logged-in session and continues the pull. If the browser is gone, D8.
8. When it is done for real it pulls its downloads, releases the hold, and stops the browser, which also ends the live URL. Conductor's reap at step exit is the backstop.

The hosted browser lives **at most 240 minutes** from its creation and the vendor offers no extend ([api-v4/browsers/update](https://docs.browser-use.com/cloud/api-v4/browsers/update-browser-session), `{"action":"stop"}` is the only action). Because substation creates the browser when the person clicks, that clock starts when the person shows up; a card that sits overnight costs nothing and works in the morning. Profiles, which would carry a login across a browser's death, stay deferred (§7).

## 2. Decisions

- **D1 — The handoff is a gate; the step that meets the wall finishes.** Fact-checked 2026-09-25: the 2.0 lane has no pause primitive. A `runner: none` gate runs no agent; an agent step that hits a wall exits 75 with a `BLOCKED.md` and "the session ends at once: no in-session retry, no resume … the step relaunches cold" (`conductor2/README.md:107-115`). Session `--resume` is scoped to one node's contract-retry loop, never across a gate (`conductor2/src/claude.rs:6-7`). Nothing is left on the table by not pausing, and the parent spec's §2 caveat that `9.7-hands` is a "seat-park" whose session replays on resume is stale: the gate is `runner: none` with `hands-done.json?` as its output (`9.7-hands/step.yaml`), and the acquire step re-reads that file cold.

- **D2 — Substation owns the browser; a hold is a short reuse window.** `noetic-browser hold --name NAME --seconds N` (default **1800**, capped by the browser's own `timeoutAt`) writes `hold_until` on the record in `scratch/browser.json`; `reap` skips a browser whose `hold_until` is in the future and says so on stderr; `release` clears it; a hold past its time is reaped as today. Nothing runs after the sandbox stops, so the hold cannot be a cost limit — the vendor's timeout is the ceiling (eight cents for a full four hours). **Substation's open-browser route** (`POST /api/runbook-hitl-questions/:id/browser/:item`, member-authenticated like the answer routes) decides on click: pointer present, `hold_until` in the future and `GET /browsers/{id}` says `active` → return `live_url`; else stop the old browser if any, `POST /browsers` with `timeout: 240`, `proxyCountryCode` matching the item's proxy flag (**null** unless the step used `--proxy` — the vendor's default is the proxy **on**, `"us"`), open one CDP websocket, send `Page.navigate` to the item's page URL, close it, store the new pointer, return `live_url`. A fresh browser opens on a blank tab and the live view has no address bar, so the navigate is not optional; if it fails the route still returns the live view and the card prints the URL to paste. Vendor claim to confirm on the pilot: that the live view stays interactive with no automation client attached (the docs do not say; if not, the route keeps one CDP connection open per browser).

- **D3 — Shared Noetic accounts; any member may see the live URL.** The login a person types into a hosted browser is Noetic's account on that portal, never a personal one. The live URL is a bearer credential for the browser's life; today any Noetic member can read the row that carries it (SELECT policy on `runbook_hitl_questions`) and the MVP accepts that, bounded by D9 (done hides it) and step 8 of §1 (the resumed step stops the browser).

- **D4 — No payment in the MVP.** Login and CAPTCHA walls only. A checkout stays a hands item the person **declines**; the acquire step already records a declined item as `not-instantly-gettable:declined-at-the-hands-gate` (`9.8-acquire/prompt.md:18`). The pilot portal is one with a free account wall (GSCCCA's limited-use account is the known case).

- **D5 — Conductor's callback carries the browser facts; the captain adds nothing.** The page URL and held-browser record are plain facts in run-directory files, not judgement calls. At park, `callback::gates_for` (`conductor2/src/callback.rs`) reads the gate's input step's `needs-hands.json` and `scratch/browser.json` and puts `items: [{document, page_url, browser: {id, live_url, cdp_url, timeout_at, hold_until, proxy}}]` on the `hands` gate. Substation's callback handler stores them (D11). A card is therefore complete even when the captain died before asking — reverses v1 D3 and closes v1 Q4. `captain.ask`'s `--live-view-url` stays as is, unused by this lane.

- **D6 — One browser per hands item.** Each row of `needs-hands.json` names its own browser and gets its own pointer, embed and open button. Two items on one portal may name the same browser (the step opened one per portal already); the reuse window applies per browser. Rejected: one browser per gate with a per-item "take me here" navigate button — it saves a login only when items share a portal, which naming the same browser also does.

- **D7 — Per-item done or declined on the card.** The card renders one row per `items` entry with a done / declined toggle and a note; the answer is `{items: [{document, outcome: "done" | "declined", note}]}`. This is the shape the acquire step already reads. Replaces the single Mark done (v1 Q3).

- **D8 — Browser gone before attach: re-ask, no cap.** The person marks done at minute 235 of a 240-minute browser, or walks away while the sandbox takes minutes to resume; `attach` finds the browser stopped. The step writes the item to `needs-hands.json` again with a note ("browser expired before the agent could attach — please log in again"), marks the record `stopped_at`, and the run parks on the same gate. The card shows how many times the item has been asked. No automatic decline and no retry cap: a person always closes the loop, by logging in again or pressing declined. Optimisation, not rule: the open-browser route may refuse to hand out a browser with under ten minutes left and create a fresh one instead. `hands-done.json`'s per-item `browser` field is additive to the contract's `{document, outcome, note}` (`9.7-hands/contract.test.ts:27-38`).

- **D9 — Done closes the person's access, per item.** On done, substation marks that item's pointer `handed_back_at`; the card drops the item's embed and button ("handed to the agent"), and the open-browser route refuses the item. This keeps two hands off one wheel once the resumed step attaches. The URL itself works until the browser stops, which the resumed step does (§1 step 8); that window is the exposure D3 accepts. Other items' browsers are unaffected. A mistaken done is repaired by D8's re-ask.

- **D10 — No browser cost recording in the MVP.** A browser substation created that nobody marked done, or one it replaced at the end of a reuse window, is in no step's ledger. Cents; ignored. If it ever matters, the open-browser route stores the vendor's reported `browserCost` on the pointer when it stops or replaces a browser, and cityhall adds it to the run's cost line.

- **D11 — One JSON column on the question row.** `runbook_hitl_questions.browsers jsonb` holds the array of pointers: `[{item, document, page_url, vendor: "browser-use", id, live_url, cdp_url, timeout_at, hold_until, proxy, created_by: "step" | "substation", handed_back_at, stopped_at}]`. The existing `live_view_url` column mirrors the first item's `live_url` so the current card keeps working until D7's card lands. No new table: a question never has more browsers than items.

- **D12 — The smoke fixture takes `directives.hold_seconds`.** Default 1800. The open step passes it to `noetic-browser hold --seconds`; **0** means the window has already lapsed when the card appears, so the click takes the fresh-browser path (create + navigate + store), and 1800 takes the reuse path. Two cloud runs cover both. The fixture stays **off by default** (`directives.hands: true` turns it on) because it spends a hosted browser and two agent steps. The vendor-timeout path (D8) is not fixture-tested in the MVP; it is exercised by hand once.

- **D13 — Ship order: substation → conductor2 (+ cloud image rebuild) → bureau → cityhall.** Each piece is harmless without the next (§4).

- **D14 — Cloud only, and only when a key is present.** On a lane with no `BROWSER_USE_API_KEY` every `noetic-browser` verb is a no-op, as today (`noetic-browser:24-26`): the local lane keeps its headed Chrome and the person at the keyboard. A local run's hands card carries no pointers and no button, which is correct — the browser is on the operator's own screen. (v1 D8.)

- **D15 — Proxyless is the default for a handoff.** The residential exit IP rotates between requests (2026-09-08 probe), and a portal that binds a login to an IP would drop the person's session before the agent got back. A step escalates to `--proxy` only for a site that refused the datacenter IP, the item's `proxy` flag records it, and substation's fresh browser matches it. (v1 D9.)

## 5. The smoke fixture

Smoke's quiz (bureau#1787) already asks a person three things they read off a Wikipedia page, one gate at a time. The handoff fixture adds the browser to that conversation, off by default (D12):

- **`2.10-open`** (worker, `skills: [agent-browser]`): opens the hosted browser at the drawn animal's article, writes `needs-hands.json` with one item — *"in the live browser, open the article of one animal linked from this page's first paragraph, and leave the browser there"* — naming the page URL and the browser, holds it for `directives.hold_seconds`, and writes `needs-hands.md`.
- **`2.11-hands`** (`runner: none`, outputs `hands-done.json?`): the hands gate. The callback ships the item and its browser; the card shows the embed.
- **`2.12-return`** (worker): attaches to `hands-done.json`'s browser, records the URL the browser is on and the page title into `handoff.json`, releases, stops.

The contract on `2.12-return` is the whole point: **the URL the person left the browser at is a different Wikipedia article than the one `2.10-open` opened.** That is the only check that proves a person's actions in the live browser reached the resumed agent, which is the login primitive itself. With `hold_seconds: 0` the browser the person acts in is one substation created and navigated, so the same check proves the fresh path. Without the key (a local run) `2.10-open` opens a local headed session instead and the check is the same.

**Acceptance for the pilot:** two cloud smoke runs with `hands: true`, one at `hold_seconds: 1800` and one at `0`, each parking at `2.11-hands` with a card whose iframe shows the article; a person navigates in it and marks done; the run resumes, `handoff.json` names the page the person chose, and `noetic-browser list` in `2.12-return` shows the browser stopped and priced. Confirm on the same runs that the live view is interactive with no CDP client attached (D2's open vendor claim) and that the exit IP held across the park (Q1). Then the same on site-research against GSCCCA.

## 6. Cost and exposure

A hosted browser bills **$0.02 per browser-hour** ([pricing](https://browser-use.com/pricing)). A held browser nobody clicks on costs at most eight cents before the vendor's timeout stops it; a browser substation created bills from the click. Neither is recorded in the MVP (D10). The live URL is a bearer credential with no expiry of its own; any Noetic member can read the row that carries it, accepted for now (D3), and it is hidden from the card on done (D9) and dead once the resumed step stops the browser.

## 7. Deferred, deliberately

- **Profiles.** Browser Use persists cookies and login state to a profile (`profileId` on create; [concepts/profile](https://docs.browser-use.com/concepts/profile)). D2 removes the need for the MVP: the browser is created when the person arrives. Profiles matter only if a portal's login must outlive one browser, and they raise their own questions (one per site or per run; where a shared login lives; write-back timing — unverified).
- **Payment** (D4).
- **Cost recording** (D10).
- **A hosted browser for a remote operator on the local lane.** Local runs keep the headed Chrome (D14). The key's presence already decides which browser a step uses.
- **The vendor-timeout test path** in the fixture (D12).
- **The site-research second pass.** `9.7-hands` is a graph sink; nothing re-runs `9.8-acquire` after it, so §1 step 7 has no trigger today. A `9.9-resume` step, or a re-run of 9.8, is a follow-up decision (v2.1).
- **D8's re-ask.** Deferred with the resume step: a fresh `needs-hands.json` item cannot re-open a gate whose `hands-done.json` already has a row per document, and the resuming step cannot write into the gate's input step's folder. An attempt number on both files and an attempt-aware contract is the real fix. **Interim:** a browser gone before `attach` parks the resuming step with a `BLOCKED.md` naming the item (exit 75, the existing operator card); the "asked N times" count on the card goes with it (v2.1).
- **Narrower visibility of the live URL** than any member (D3).

## 8. Open questions

- **Q1 — IP-bound sessions.** Proxyless is the default and its IP should be stable within a browser, but that is asserted, not measured. Confirm on the pilot portal before trusting a login across a park.
- **Q2 — Live view with no automation client.** The vendor docs say the live view is interactive and that a closed CDP connection does not stop the browser, but not whether the view stays interactive while nothing is connected — the exact state of a held browser. Confirm on the first fixture run; the fallback is one open CDP connection per browser held by the open-browser route (D2).
