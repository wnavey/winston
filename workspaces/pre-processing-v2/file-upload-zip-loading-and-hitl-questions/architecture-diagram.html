why two tables, not JSONB-on-job The ask/answer pair is an addressable, auditable resource with race-safe resolution (WHERE status='pending'), and a job can carry a sequence of questions over time. question_type keys a closed registry — a substation detector, a cityhall component, and a resolver per type — mirroring the existing Rich Card Message registry (rcm/components.ts). New ambiguities are new types on the same transport (D-tables, D-registry).

Precedence + argmaxDeciding which question to ask

Every incoming file runs a fixed precedence: exact hash first (certain, short-circuits), then one flavor-routed similarity pass that produces at most one decision against the single best candidate. If nothing clears threshold, no question is asked and the file auto-attaches.

argmax spans types The best doc↔doc match and the doc→plan-set cross-type match compete — the single global winner is asked (D25). Wrong-top-1 is accepted: if the true match is 2nd place and the user answers separate, the real match is missed — rare, and far better UX than a "is this A? …is this Z?" barrage. The separate/keep options cleanly cover "no, these differ."

reading the numbers The text cutoffs (0.60, 0.98) are shingle-Jaccard values — comparable only against a k=3 build; re-seed them if k changes. The visual ~0.70 is a doc-level score after matchSheets has dropped page-pairs below 0.5. The exact-hash pre-check (Tab 03) has no threshold — byte equality, evaluated first.
highest-leverage de-risk (Q-detection) The 0.7 visual number was never validated, and greyscale raster is the weakest signal for text forms — which is exactly why the trace's near-identical-name, content-revised documents route to text. Validate every cutoff against ~10 real resubmittal pairs before building Phase B detection. Start with pure per-flavor routing; add the visual/text booster only if validation shows false negatives.
certainty vs. fuzziness — why both exist The exact-duplicate hash (Tab 03, step ①) is a separate, earlier check: 0 false positives and it short-circuits rasterization for true re-uploads. Similarity ≈1.0 would eventually catch identical bytes too, but only after paying the full rasterization cost — so the hash owns certainty + skip, and these fuzzy routes own near-duplicate / revised-version detection (D22/D27).

Off-slot hold · attach-only-on-resolveWhere staged files & their rows live

The core invariant: an incoming file is never in the live submission set until its decision resolves. A held document is fully processed but its junction row is withheld; a held plan set's bytes are parked at a staging key. No live duplicate ever appears (D15).

wherePhysical storage of the bytes

staging · …/uploads/{job_id}/… — landing zone from the browser PUT; file_upload_job.storage_path points here first
held document · normal document location — bytes + per-page rasters are fully written; only the submission_document junction row is withheld. Rasters are already available for the Pending-section thumbnails (no re-upload)
held plan set · pending/… off-slot key — bytes are NOT moved to the canonical single-occupancy source key until version/replace/keep resolves. The existing plan set stays live; produced_plan_set_id stays null
verify at build time The exact storage-keys.ts helper (planSetSourceKey) was not re-verified in this pass. The single-occupancy constraint is only on the canonical source key; the submission_plan_set junction already permits a transient second link, so the held plan set needs no schema change — confirm the helper name before relying on the pending/… key.

the tree proceeds independently A decision blocks only its own job's finalization (D2) — never the parent zip or sibling children, which reach done on their own. The parent zip → done at end of extract; "still processing" is derived from the child tree (D5). No stuck-processing watchdog in v1 (D7).

surfaceWhere the held file is visible to the user

the "Pending" section (D20) A held decision renders inline on the current submission version's page, directly above the "Plan Set" row — not a modal. One full-width row per open decision, stacked when several are open. Version/replace/promote rows show side-by-side thumbnails (incoming page-1 raster vs. the matched existing file's, whose thumbnail links to its document/plan-set page). Each row's top-right 'X' = discard, gated by a "This will discard the uploaded file {filename}. Are you sure?" confirm modal. Supabase Realtime keeps the section live — rows appear as detection creates decisions, disappear as they resolve. No timeout (D18): the held file waits off-slot until answered.
