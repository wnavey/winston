Overview

One request names a cartographer_files row. Fourteen steps later, that file's figures sit in cartographer_geometries as SRID:0 polygons, placed relative to one another, with every reading's crop stored as evidence. Seven steps are agent work (three of them fan-outs), five are scripts, two are gates.

What the runbook is for

  1. Geometry off a recorded plat. A plat or boundary survey prints each lot, right-of-way and easement as a walk of bearing-and-distance calls: in prose (THENCE N 03°53'40" E 249.10 FEET), in line and curve tables keyed L1, DE7, or as labels along the drawing's lines. The runbook reads all three forms and turns each figure the plat describes into one closed polygon in its own local frame (SRID:0), not yet tied to the ground.
  2. Agents transcribe, code computes. No agent produces a coordinate, an area, a closure verdict or an offset. Readers report the call exactly as printed plus a structured decomposition of it, and cartographer's src/lib/geometry does every piece of arithmetic. A misread bearing then shows up as a wrong shape or a large misclosure, where a "computed" polygon would hide it (AGENTS.md rules 1–2).
  3. The code is cartographer's. This is the conductor port of cartographer's prose-orchestrated runbooks/extract-geometry, step for step. Every deterministic piece (crops, tiles, the traverse engine, evidence, placement, publish) runs from the cartographer checkout named by $CARTOGRAPHER, so what the run publishes and what the app draws stay one code path. scripts/carto bridges the two layouts: each step gets a v1-shaped workspace <step>/ws/ with the source PDF and every crop the run's other steps made linked in.
  4. It records what anchoring needs. The survey marks the notes block as a plat_notes region; the transcriber reports the basis of bearings, distance units, grid or surface, the combined scale factor and every printed N:/E: coordinate box; the merge carries them onto each figure, coordinate boxes as controlPoints by vertex (winston#279 D6).
  5. Publishing replaces. 7.1-publish runs only on a publish ruling, and it deletes every figure the file already has, with its evidence and crop objects, before inserting this run's. There is no undo. A comparison run rules stop.

The rules every agent follows

From the runbook's AGENTS.md, prepended to every agent step after the shared core rules. They exist because the failure mode is confident misreading of small text on a scan.

  1. Values are read off crops rendered from the PDF. The 150 DPI page rasters and the survey tiles are for finding blocks, never for reading a bearing.
  2. Small text is read at native pixels. The harness shows every image at about 1568 px on its long edge, so a 600 DPI crop arrives at a fraction of its resolution. Readers cut it with crop grid and crop subcrop and read the pieces.
  3. The scan's own resolution is the ceiling. source.json records nativePpi per page; a render above it invents pixels, so "re-crop bigger" is not an escalation once a crop is there.
  4. Rotation is carried into every crop. Plats are often drawn sideways, and sideways small text is where a vision model transposes digits.
  5. Every image is made by the crop tool. Each crop gets a sidecar crops/<id>.json saying where on the page it sits, and only a reading from a crop with a sidecar can be published as evidence and drawn back onto the PDF. Crop ids are global to the run and prefixed with the worker's item id.
  6. A bilevel scan is eroded, not thresholded. On 1-bit CCITT, -morphology Dilate Disk:1 reopens a filled counter; a level stretch does nothing.
  7. A number someone hands you is a hint. A stated acreage or course count helps notice a missing course; it is never grounds to change a digit.
  8. Labels use the plat's own words. LOT 1, 15' SANITARY SEWER EASEMENT, never the runbook's process vocabulary.

How a crop made in one step is visible in every later one

Each step gets its own v1-shaped workspace. cartographer's scripts take a single run directory with source.pdf beside crops/ and tiles/. Before every script call, scripts/carto runs ws.py, which fills <step>/ws/ with a symlink to 1.2's PDF and symlinks to every crop and tile any other step has made, then runs the script against that folder. Whatever the script writes stays in the calling step's folder.

Fan-out siblings are not linked. A sibling item runs beside the worker, is never its input, and may still be renaming a crop it is making, so ws.py skips it. A link whose target has gone is dropped, and a crop name two steps both made is reported as a collision rather than guessed.

Crop ids are global to the run. The crop tool refuses to overwrite an existing id, so every worker prefixes its crops with its item id (p2-r3-de7-row). The contracts that check citations (3.2, 4.1) search every ws/crops/ one or two levels under the run root for the sidecar, through crops.ts.
