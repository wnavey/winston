verbatim is optional on a course mete.courses[].verbatim is absent whenever a figure was not built from metes-and-bounds strings — a coordinate-table reconstruction, a side computed to close a ring, an imported geometry. Absent means not read from a printed call; unreadable means read, but a digit was destroyed. Different things. On evidence the field stays NOT NULL, because a row with nothing read is not evidence — open as Q7.
why two tables They have different cardinality. Twenty-one table rows are read from one crop, and one crop may be cut from another crop. Folding crops into an evidence column would duplicate the image metadata per row and leave nowhere to record the chain.
the one thing to decide D1 makes both tables children of a geometry, not of a file. Simple lifecycle, one cascade — but a line shared by two figures is stored twice, and evidence that was read and deliberately not used has no home. Costs are on tab 4; open as Q1/Q2.

Section 2A crop is a chain, not a rectangle

D1What geometry-scoped ownership costs

A shared line is stored twice

R/W Dedication Area 3 walks Lot 1's frontage call in reverse (reversed = true). Both figures get their own evidence row pointing at the same rectangle on the page. Bounded, and the rows are small.

Rejected evidence has no home

The run read the split-segment pieces, the old interior lot lines and the R/W width dimensions, and deliberately used none of them. They can only attach to a figure they were weighed for, as role = 'context' — or not be stored. Q2.

The crop chain is per figure

Two figures reading from the same table crop each get their own crop row and their own uploaded copy. At delivered resolution (D7) that is tens of kilobytes, not megabytes.

What it buys

One owner, one cascade, no orphan sweep, and no second lifecycle to reason about when a figure is replaced. The alternative — file-scoped evidence plus a join table — is additive later if the duplication grates. Q1.

Storage: bucket cartographer-files · path <file_id>/geometry/<geometry_id>/crops/<crop_id>.jpg — keyed by geometry so the sweep path is obvious. The migration adds image/jpeg to the bucket's allowed types; it was created for PDFs and PNG thumbnails only.
open Q6 — placement can be redone without re-reading the plat (winston#270 D1), but publish.ts deletes and reinserts figures wholesale. A placement-only re-run would destroy and rewrite evidence it never looked at.

Section 5What the numbers in a box actually mean

A rectangle is meaningless without the frame it is measured in. Both evidence.bbox and crops.box use one convention, stated here so a consumer never has to guess.

the conventionbbox = [x0, y0, x1, y1] each a double in [0, 1] x = fraction of PAGE WIDTH origin: TOP-LEFT y = fraction of PAGE HEIGHT y increases DOWNWARD measured against the UNROTATED MediaBox x_points = x * page_width_pt x_inches = x_points / 72 y_pdf = page_height_pt * (1 - y) # PDF user space is y-UP invariants: x0 < x1, y0 < y1, all clamped to [0,1]
pages don't share a size They don't even share one inside a document. This plat: page 1 is 648 × 789.84 pt (9 × 11 in, the clerk's cover sheet), page 2 is 1728 × 2594.16 pt (24 × 36 in, the plat). That is why nothing absolute can be stored, and why page_width_pt / page_height_pt ride on every row.

whyThe three candidates

OptionPrecision on the 36-inch sheetVerdict
Normalized doubles 0–16 dp = 0.000036 inchosen — already what survey boxes, the tile manifest and remapToPage speak
Fixed integer grid 0–10001 unit = 0.036 inrejected — a digit glyph is 0.05–0.08 in tall, so it quantizes to half a glyph and can point at the wrong table row
Absolute PDF pointsexactrejected — every consumer must fetch page size before it can draw; solved instead by denormalizing the two dimensions
the sharp version The harness downsamples to ~1568 px on the long edge before a model sees anything, so one pixel the worker actually saw is 36/1568 = 0.023 in. A 1/1000 grid (0.036 in) is coarser than the model's own pixel — it would discard information the worker genuinely had. Beating that pixel needs ~1/10,000, which is a double with extra steps. And a box cut from a recorded 600-DPI crop is good to 0.0017 in.
two silent traps (1) PDF user space is y-up from the bottom-left; every crop, tile and vision worker in this pipeline is y-down from the top-left. A mismatch mirrors every box vertically and still looks plausible. (2) A page's /Rotate is not the runbook's viewing rotation — both pages here are /Rotate 0, and the drawing is sideways in the scan itself. pdf.js applies /Rotate by default, so a viewer must pass rotation: 0 or compensate.
blocking prerequisite remapToPage (lib/page.ts:97) is plain linear math and never reads the manifest's rotate. Until that is fixed, every box this model stores would be wrong on any page a worker views rotated — which is this plat.
