**Audited:** `DESIGN-SPEC.md` Draft v1.1, against bureau main @17a0bcc343, cityhall main @2c1f1db, inspector-general @d7b928e, completion-officer @5e75ade, and read-only SQL on the prod App DB (`mgxqsrjutswbciyrltwd`).

## 1. Versioning

**A1. One backfilled revision cannot resolve the 19 v2.7-trimmed reviews.** *(high)*

D5 backfills today's v2.7-trimmed content as revision 1. But that label has held 6 distinct contents:
- IG's cache holds 14 rows for it. Versions 1–2 have 194 items; versions 3–14 have 192.
- The 19 reviews that ran on it span 14 bureau commits. Those commits resolve to 7 different states of the folder (git tree hashes), and **none of them is the folder as it is today** (tree `d7ffe14`, after #2105). Reviews per state, oldest first: 3, 1, 5, 2, 4, 3, 1.
- Comment numbers changed under the label too. Review 31fb1daa (2026-10-12) used the pre-#2105 map, and 159 of its 192 numbers differ from today's file.

So "join a review to its items through its version and revision" (§6 Not yet specified) would join most v2.7 reviews to content they never ran against.

- **Proposal:** backfill v2.7-trimmed's history, not just its tip.
  1. Walk `git log -- jurisdictions/austin/completeness-check/v2.7-trimmed` (18 commits) and build one version per distinct content.
  2. Record every folder commit in a lookup table, `intake_checklist_version_commits (checklist_id, version, bureau_commit)`.
  3. A review resolves through `reviews.metadata.bureauCommitHash` → the newest folder commit that is an ancestor of it → that version.

  The ID set is identical across IG versions 3–14. The two items dropped on 07-09 get IDs 0193 and 0194, which are retired at once, and `next_item` becomes 195.
- **Cost:** one script, about 20 versions. It also makes Q1, older labels, the same mechanism applied to more folders.
- **Decision:** backfill v2.7 history now (recommended), or accept that pre-tip v2.7 reviews don't resolve.

**A2. Give every checklist version a semver, declared in bureau and stamped on each review.** *(high)*

Today a version is `(label, revision)`. `label` is a folder name that is edited in place, and `revision` is a counter the DB assigns. That means:
- bureau never knows the revision;
- a review can't record it without reading the DB;
- the number says nothing about how big the change was.

No data format in the repos uses semver today. `output_schema` uses dates, and JSON formats use an integer `schema_version: 1`. The only semver is the RDS npm packages.

- **Proposal: content semver.** Each version dir gets a small `version.yaml`:

  ```yaml
  version: 1.4.2        # semver of this checklist's content
  format: 1             # the file-format version (see "Format version" below)
  generated_by: …       # A6
  ```

  `PK (checklist_id, version)` replaces `(checklist_id, revision)`; `label` stays as the folder name, for display. The bump is **computed** by `lint:intake` from a diff against the same dir on `origin/main`. The declared version must be at least that bump. The proposed rules, from the consumer's point of view:

  | Bump | When | Why |
  |---|---|---|
  | MAJOR | an item ID leaves the checklist (removed, split, merged) | answer keys, IG mappings and old reviews can no longer map one-to-one |
  | MINOR | an item is added, or what an item checks changes (`item_text`, `condition`, `location`, `location_binding`, `requirement_source`, `source_type`, `fail_status`) | the review's verdicts are no longer comparable for that item |
  | PATCH | anything else the version stores: titles, citations, group placement and order, group titles, comment numbers, guide prose (A3) | output reads differently; what is checked is the same |

  The sync then requires `(checklist_id, version)` to arrive with one content hash. A second hash under the same version fails the job, which catches a content change that wasn't bumped.
- **Stamping:** the CC runbook's 1.4-resolve already reads the version dir. It would copy `version` into `resolved.json` and from there into `reviews.metadata.intakeVersion`. Every future review then names its exact version with no DB lookup and no commit archaeology. That belongs to the review-linkage spec (§8).
- **Format version:** `format` is an integer, following the `schema_version` precedent. A breaking change to the file layout bumps it, and the sync refuses a major it doesn't know. This matters now because north-star Q1/Q2 are expected to reshape the format after non-Austin runs, and #2112 already writes it.
- **Questions for Will:**
  - **Q-A2a:** is regrouping or renumbering PATCH? Comment numbers are customer-visible, so it could be MINOR.
  - **Q-A2b:** where do numbers start? Recommended: `1.0.0` for each checklist's first synced content, computed forward. The alternative is to seed Austin at `2.7.0` to echo the label, but the 194 → 192 removal would immediately make it `3.0.0`.
  - **Q-A2c:** does a revert to earlier content need a new version? Recommended: yes, always forward (A13).

## 2. Markdown in Supabase Storage

**A3. A version should identify every byte the CC runbook reads; mirror the files to Storage, content-addressed.** *(high)*

D10 leaves guide prose out of the hash and out of the DB, so two different sets of guides can share a revision. But the review agents read Key Terms, Documents to Review and Validation Methodology, and those are part of what produced a review. The runbook already treats them that way: 1.4-resolve records `checklistsTreeHash`, and amend refuses when it changes.

- **Proposal:**
  1. The sync uploads every file the runbook reads from the version dir to a private bucket, `intake-checklists`, before calling the RPC. Those files are the guides, the title map, `true-comment-num-mapping.tsv` and `source-citations.json`.
  2. Paths are content-addressed and immutable: `<checklist_id>/blobs/<sha256>`. Precedents:
     - the SIR assets, `/assets/<sha256>`, "one name is one set of bytes", `cityhall/src/lib/publish/sir.ts:277`;
     - the PPv4 publish path, which moved to a hash after the CDN-staleness bug on run 164a31d7;
     - the immutable `cc-source-snapshots` snapshots.

     Unchanged guides are stored once across versions.
  3. A new table holds one row per file per version:

     ```sql
     intake_checklist_files
       checklist_id, version   FK → intake_checklist_versions
       path        text        -- 'cc-1.md', 'cc-item-title-mappings.tsv'
       role        text        -- guide | title_map | numbering_map | citations
       group_id    text NULL   -- for guides (A5)
       sha256      text        CHECK (sha256 ~ '^[0-9a-f]{64}$')
       byte_size   int
       storage_path text       -- '<checklist_id>/blobs/<sha256>'
       PK (checklist_id, version, path)
     ```

     The column set follows `cartographer_files` and `document_version`.
  4. `content_hash` covers the item rows plus the `(path, sha256)` manifest, so a prose edit is a PATCH (A2).
- **Transactions:** a Storage upload can't join the RPC's transaction, so the order is upload first, then the RPC. The RPC checks `storage.objects` for every `storage_path` in its payload and raises if one is missing. A failed run leaves only orphan blobs, which are harmless because they are content-addressed.
- **Access:** an authenticated-read policy on the bucket, as `cc-source-snapshots` has (`schemas/storage/tables/objects.sql:1-10`), plus `workflow_run` read for A4's 1.4-resolve. Whether a Storage policy can target `workflow_run` is **unverified**.
- **Alternative:** `content text` in the table, as `bureau_nodes` does (329k rows, written by `sync-bureau.ts`). That keeps everything in one transaction. Will asked for Storage, and guides are small either way.
- **Precedent worth knowing:** conductor2 already persists each run's step files to bucket `runbook-runs`. For example, `runbook-runs/<runbookRunId>/steps/1.4-resolve/checklist/cc-*.md` exists for run e2e0cb2d, so persisted CC runs already keep the exact guides they read. That covers new runs only, and only when persisting.
- **Decision:** store the files, and hash the prose (recommended)? Storage or a text column?

## 3. Toward the DB as the source of truth for CC runs

**A4. Plan the flip as five steps, and land the first in this spec.** *(medium; mostly sibling-spec scope)*

Today the CC runbook can read only a bureau checkout. `checklistsDir` is bureau-relative (`cc.py:226`), and 1.4-resolve copies the dir to `$RUN/1.4-resolve/checklist/`, "the only place the run reads guides from". That copy is the seam: swap where it copies from and nothing downstream changes.

| Step | What | Door |
|---|---|---|
| M0 *(db-schema v2)* | The DB and Storage hold every file and item for every version, keyed by semver (A2, A3) | two-way |
| M1 *(review-linkage)* | 1.4-resolve stamps `intakeChecklist` + `intakeVersion`; 2.9-comments adds each finding's stable `itemId` from the sidecar, which is already in the run dir | two-way |
| M2 *(source-of-truth)* | **Shadow:** 1.4-resolve also materialises the same version from Storage and compares the `(path, sha256)` manifest to the bureau copy. It logs any mismatch and still runs from bureau | two-way |
| M3 *(source-of-truth)* | **Flip:** 1.4-resolve reads from the DB/Storage by `(checklist, version)` under the `workflow_run` role (D7 already grants it SELECT). Bureau still syncs into the DB | two-way (flag) |
| M4 *(source-of-truth)* | **Reverse:** edits are made in the app, as new versions with `origin = 'app'`. Each is exported to bureau as a PR to ratify it, which is the `jurisdiction_departments` `origin`/`verified` pattern, or bureau's copy is retired | one-way |

- **M4's prerequisite is a renderer.** A guide must be generated from structured parts, `render(prose blocks, item rows) → cc-N.md`. That needs a round-trip test, `parse → render`, byte-identical on every synced guide. Cedar Park's `cc-21.md:86` would fail it today, which is exactly the kind of row the test exists for (A16).
- **The runbook rule:** north-star D10 says "runbooks never write the DB". M3 reads, which is allowed, but the north star should say so explicitly.
- **Decision:** agree M0 belongs in db-schema v2 and M1 in a review-linkage spec, with M2–M4 in `intake/db-source-of-truth`?

## 4. Groups, tracked apart from items

**A5. Today a group is a file, a ref prefix, a section slug and an LLM work unit. Give it its own identity.** *(high)*

What depends on the group today:
- **The work unit:** the guide file is the fan-out unit, one roster entry per guide × run.
- **Group order:** `reviewFiles` must match `^cc-\d+`, and guides sort by the digits in their names.
- **The section:** the group title is parsed from the H1 with `^#\s+CC-\d+:\s*(.+)$` (`enrich-findings.ts:110`). It becomes `sectionName` and `applicableArea`, and `slugify(title)` becomes every comment's `output_json.section`. The docstring warns: "a slug that changed would orphan every comment under a heading".
- **The ref:** it is `{guide stem}:{ID}`.
- **Comment numbers:** they follow group order.

The v1.1 schema stores `group_key` (`cc-1`) and `group_title` (the H1, including its `CC-1:` number) on every item row. So the group has no identity of its own, its title embeds its position, and moving an item changes its row's `group_key`. That is a fact about the item, not about the group.

- **Proposal: three layers.**
  - **Identity:** who exists, with stable IDs.
  - **Placement:** where things sit in a given version.
  - **Content:** what an item says in a given version.

  ```sql
  intake_groups           (checklist_id, group_id)                        -- identity: 'austin-g01'
  intake_items            (checklist_id, item_id, derived_from[],         -- identity: 'austin-0042'
                           minted_in_version, retired_in_version)          -- computed by the sync (A6)
  intake_version_groups   (checklist_id, version, group_id,               -- placement + title, per version
                           position, title, guide_path)
  intake_version_items    (checklist_id, version, item_id,                -- placement + content, per version
                           group_id  FK → intake_version_groups,
                           position, comment_number,
                           title, item_text, condition, …, fail_status, citations)
  ```

- **What that buys:**
  - Moving an item changes only `intake_version_items.group_id` and `position`. Its `item_id` and `title` are unchanged, and so is every group's `group_id` and `title`.
  - Renaming a group changes only `intake_version_groups.title`.
  - Reordering groups changes only `position`.
  - Each is a PATCH under A2, and a diff between versions can name it as a move, a rename or a reorder rather than "a new revision".
- **In bureau:**
  - Group IDs are minted like items: `{checklist}-g{NN}`, from a `next_group` high-water mark in `intake.yaml`.
  - A new per-version `intake-groups.tsv` (`stem`, `group_id`) maps each guide file to its group.
  - The stored title drops the `CC-N:` prefix, because the display number is positional.
  - Guide files stay the runtime unit, so moving an item is still moving a table row between `cc-N.md` files. The sidecar keeps its ID, and the linter accepts the ref change.
- **The runbook side (review-linkage spec):** the runbook should key sections on `group_id`, not on `slugify(title)`, and comments on `itemId`, not on the group-prefixed ref. Until it does, a regroup still changes refs and section slugs in new reviews. It doesn't break old ones, because they resolve through their own version.
- **Decision:** adopt the identity/placement split in db-schema v2 (recommended)? Group ID format? Strip the number from titles?

## 5. Tracking the runbook runs that generated a checklist

**A6. Record which run produced a version, and compute which version minted each item.** *(medium)*

Today:
- `intake.yaml` `decided_by` is "a person, or a runbook run id". But #2112's code writes `run.name`, the run directory's name (`step_write.py:97,109`), not the `runbook_runs.id` uuid that `conductor init` creates.
- With no control plane configured, a run has no uuid at all.
- For local runs, `runbook_runs.runbook_ref` is `'main'`, not a commit.
- cc-source-citations' JSON carries `runbook_run: "austin-v2.7-trimmed"`, also a directory name, and strips it as volatile.

- **Proposal:**
  - `version.yaml` gains:

    ```yaml
    generated_by:
      runbook: intake-prospecting
      run_id: <runbook_runs.id uuid>
      run_name: <dir name>
      runbook_commit: <sha>
    ```

    It is absent for hand edits.
  - The sync stores `generated_by` on `intake_checklist_versions`, plus a `generated_by_run_id uuid` with no FK, because runs can come from another environment.
  - `intake_items.minted_in_version`, `retired_in_version` and therefore the minting run are **computed** by the sync from version history, not authored.
  - `intake.yaml` splits the two meanings of `decided_by`: who ruled on the **basis**, and the run that generated the checklist. The run is a reference to `generated_by`.
  - intake-prospecting should refuse to publish with no `runbook_runs` id, or record `run_id: null` explicitly.
- **Cross-spec fix:** prospecting-runbook D13 says `decided_by` = "the run id", while #2112 writes the run name. One of them should change.
- **Decision:** adopt the `generated_by` block. Must a published run have a uuid?

## 6. Review counting

**A7. Define what a count is before building one; derive it from stable item IDs.** *(medium; ask Will what "review counting" should answer)*

What exists:
- A CC review writes one `review_comments` row per item, whatever the verdict.
- Votes are not rows. They sit in `output_json.sourceFindings[].perRunFindings[]` (run-1…N), with `runCount`, `totalRuns` and `voteBreakdown`.
- Promote (cityhall#347) rewrites a comment from one run, keeping the original under `promotion.replaced`. Staff can also override verdicts (`comment_triage.verdict_override`).
- Amend (bureau#2100) rewrites a published review in place.
- Per-item statistics exist only in Inspector General:
  - `ig_eval_data`: 163,832 rows, one per (IG run, item);
  - `ig_checklist_diff_mapping`: a hand-built cross-version item map, which stable IDs replace.
- cityhall tallies verdicts per section at render time (`adapters/checklist.ts:200-218`).

Counting "per item" needs a rule for each of these:

| Question | Recommended rule |
|---|---|
| A review with `runs: 3` | one count; the votes are detail |
| Amended in place | one count, the current state |
| A re-review of the same submission (`priorReviewId`) | count both; flag the chain |
| Promoted run or staff override | count the **final** verdict, and keep the agent's verdict beside it |
| Internal and test projects | excluded by a project flag |
| Same item, different versions | one series per `item_id`, with the version on each row |
| Comment numbers | never a count key: they changed under one label (A1) |

- **Proposal:** a cityhall view, `intake_item_review_outcomes`, with one row per `(review_id, checklist_id, version, item_id)`. Its columns are `agent_status`, `final_status`, `runs`, `votes` and `overridden`. Each review resolves through its stamped `intakeVersion` and `itemId` (A4 M1), or, for history, through the commit lookup and `legacy_ref` (A1). Counts are then `GROUP BY item_id`, across versions, because the ID is stable.
- **Decision:**
  - What should review counting answer? For example: how often each item fails; how many reviews a version served; reviews per jurisdiction.
  - Agree the rules in the table.

## 7. Other defects

**A8. P2a breaks review amend for every pre-sidecar v2.7 review.** *(high; blocks P2a)*

1.4-resolve records `checklistsTreeHash = git rev-parse HEAD:<dir>` (`cc.py:298`). Amend refuses when it differs ("the guides changed", `review_amend.py:83-85`, `publish_review_cli.py:436-447`). Adding `intake-ids.tsv` to the dir changes that hash, so after P2a merges, amending any of the 19 v2.7 reviews is refused. A2's `version.yaml` and A5's `intake-groups.tsv` would do the same.

- **Options:**
  - (a) Amend compares a hash over the files the run reads, ignoring `intake-*` and `version.yaml`, and falls back to the git tree hash for old reviews.
  - (b) The intake files live outside the version dir, e.g. `completeness-check/.intake/<version>/`.
  - (c) Accept the break.
- **Recommendation:** (a), in P2a.

**A9. The first merge for a new jurisdiction races `sync-conventions`.** *(medium)*

`intake_checklists.jurisdiction_slug` and `jurisdiction_intake.jurisdiction_slug` are FKs to `jurisdictions(slug)`, which `sync-conventions` writes. intake-prospecting's 3.1-write adds the `conventions.yaml` stub and `intake.yaml` in the same PR. On merge, two independent Actions start, and if `sync-intake` wins, the FK fails. D1's argument covers intake rows racing each other, not this.

- **Proposal:** make the intake sync a second job of `sync-conventions.yml` (`needs: conventions`), or chain it with `on: workflow_run`.

**A10. Concurrent PRs can mint the same ID.** *(low–medium)*

Two PRs that each take `next_item: 193` make the identical edit `193 → 194`, which git merges cleanly. Each PR's lint passes. If both IDs land in one version, the sync fails on main. If they land in different version dirs, nothing catches it, and one ID means two items.

- **Proposal:**
  - Run `lint:intake` on push to `main` as well as on PRs.
  - Add a sync check that an `item_id`'s first appearance is unique across versions.
  - Ship a `bun run intake:mint` helper, so hand edits never pick numbers by hand.

**A11. The item ID CHECK accepts another checklist's prefix.** *(low)* `item_id LIKE checklist_id || '-%'` accepts `new-braunfels-0007` in a checklist named `new`. Use `item_id ~ ('^' || checklist_id || '-[0-9]{4,}$')`.

**A12. Citations can be stale against their item.** *(low–medium)* 9 of v2.7's `source-citations.json` entries quote item text that #2057 later changed, so D9 would store citations whose `item_text` disagrees with the row. Any citation refresh also makes a new version.
- **Proposal:** the sync compares `item_text_sha` with sha(normalize(`Item`)) and stores `citations_stale boolean`, and lint warns.
- A related problem: `/intake-checklists/<j>/<ref>` resolves against `CURRENT_VERSION`, not the review's version, so links from old reviews show today's item. Versioned links fix that once the tables exist.

**A13. D11 is wrong after a revert.** *(low)* If content A → B → A, step 2 finds A's hash, writes nothing, and makes revision 1 current again. The newest revision is then not current, contrary to D11. A2 removes this: a revert is a new version with A's content.

**A14. `fail_status` NULL means `fail` at run time.** *(low)* The runtime parser defaults a missing `Fail Status` to `fail` (`checklist-policy.ts:99-110`), but D6 stores NULL for 71 Austin items. The app and the runbook would disagree on what those items do.
- **Proposal:** store the effective value, plus `fail_status_declared boolean`.

**A15. Project and customer overlays sit in the checklist dir.** *(low)* `1700-s-lamar-forced-outcomes.tsv` belongs to one project, and `pape-dawson-comment-num-mapping.tsv` to one firm. Both live in the version dir. They are not checklist content and should stay out of the version hash and A3's file manifest. Their own home is a later question, north-star Q8.

**A16. Parser drift.** *(low–medium)* Bureau has five guide-table parsers with three rule sets, and the sync would add a sixth. The behaviour that matters is the runtime's, `checklist-policy.ts`.
- **Proposal:**
  - S1 adds a golden check: the sync parser and `checklist-policy.ts` agree on refs and effective fail status for every synced version.
  - Lint adds "row cell count = header cell count", which catches Cedar Park `cc-21.md:86`.

**A17. #2112 sets the format before the linter exists.** *(process)* P2a is meant to land first as the runbook's output contract, but open bureau#2112 already writes `intake.yaml` and `intake-ids.tsv` without a linter. Whichever merges first fixes the format on main.
- **Proposal:** land P2a's `lint:intake` before #2112 merges, and include A2's `version.yaml` and `format` if adopted, so #2112 rebases onto the contract.

## 9. Should the CC runbook read its checklist from the DB at all?

**A18. Keep bureau files as the source of truth for jurisdiction checklists, at any scale we can foresee. The DB holds a read replica and, later, app-owned overlays. Don't plan the flip.** *(strategic; added 2026-10-15)*

Will asked this before investing more in DB-ification. The question is whether the CC (intake) runbook should eventually read its items from the App DB (north-star §4.5, A4 M2–M4) rather than from bureau files. The perspective is scaling intake to every authority having jurisdiction in the US through intake-prospecting. Evidence gathered 2026-10-15, read-only.

### 9.1 How the rest of the pipeline already works

**Every content type prospector makes is bureau files that a runbook reads from a checkout. The DB copies feed the app.**
- **Formal review:** it reads its guides from `$BUREAU/jurisdictions/<j>/review-guides` (`runbooks/review/steps/3.1-guides/step.yaml:11-16`). It has no request input for them.
  - The guides come from guide-training, nested unchanged inside prospector's `4-review-guides`. They ship as bureau PRs.
  - `sync-bureau.yml` replicates them into `bureau_nodes`: 328,970 rows, `.md` only, no commit stored. Only cityhall chat (codes) and Inspector General's citation resolver read that replica; no runbook does.
- **Conventions:** `conventions.yaml` is replicated into `jurisdictions` and `jurisdiction_departments`, and bureau wins. The CC runbook's 1.4-resolve reads that replica through the per-run `workflow_run` token (`cc.py:258-269`). That is the one place a runbook reads bureau content from the DB, and it is reference data, not something the run's agents read.
- **The CC checklist:** 1.4-resolve copies the guides from the checkout ("the only place the run reads guides from"). The app's `/intake-checklists` pages read the `cc-source-snapshots` bucket, which `sync-cc-sources.yml` fills on merge. No table holds an item.

### 9.2 What scale looks like today

- **Volume:** 507 bureau PRs merged between 2026-09-15 and 2026-10-15, about 98% agent-authored.
- **Prospector's PRs:** its 30 jurisdiction-run PRs changed a median of **2,256 files** each (max 6,597), and merged with no human gate in a median 11.5 minutes.
- **Bureau's size:** 311,600 tracked files, `.git` 2.6 GB. A blobless sparse clone, as prospector uses, takes 3.8 s. CI's median is 10.4 min.
- **Concurrency:** a per-jurisdiction lock in the Library DB, plus disjoint `jurisdictions/<slug>/` paths. Conflicts park a run with `MERGE-CONFLICT.md` and are rare.
- **A checklist is small by comparison:** about 20 files for a jurisdiction with its own checklist, and one `intake.yaml` for a baseline one. At about 2,000 jurisdictions, all with their own checklists, that is about 40,000 files, roughly 13% of bureau today. It is less, because many will be `none_found`.
- **How checklists change:** only Austin and Cedar Park have CC content. 17 of v2.7-trimmed's 18 commits are Claude-co-authored PRs directed by Will, and edits are small (e.g. +82/−37 across 6 files).

### 9.3 Facts that cut both ways

- **A DB read is technically cheap.** The CC runbook already reads the App DB: the submission at 1.2, `project_facts` at 1.3 and `jurisdictions` at 1.4, all through a minted `workflow_run` JWT (`cityhall/src/lib/runbook/run-token.ts:152-169`). It also writes `reviews` at 3.1. North-star D10's premise, "conductor2's rule that runbooks don't touch the DB", is wrong. conductor2's DB-free rule is about the runner binary (`src/init.rs:8-10`), not the runbooks it runs. D10 stands only as a policy choice for checklists, and v1.3.1 of the north star now says so.
- **The runbook needs bureau anyway.** The CC runbook's own code (`runbooks/completeness-check/`, and the `workflows/completeness-check/scripts/` it shells out to) lives in bureau. Reading items from the DB would not remove the checkout.
- **Traceability is per-runbook work, not free.** CC reviews record `bureauCommitHash` (59 of 60) and `checklistsTreeHash`. Runbook formal reviews record neither (0 of 11), even though they read the same kind of checkout.
- **Nothing refreshes a checklist automatically today.** `sources/manifest.json` holds fingerprints for Austin's 28 source snapshots: sha256 of the original, text and words, plus etag and Last-Modified. No job re-fetches and compares them. Prospector's freshness is age-based (`lib/freshness.json`: 14 days for active jurisdictions) and has no intake workstream. If Austin changed its CC Submittal Checklist today, nothing would notice.
- **No editor exists.** No UI edits checklists or guides anywhere. `/intake-checklists` is read-only, and `jurisdiction_departments`' two `origin = 'app'` rows were written by a runbook, not a person.
- **Migrations are a person's step.** "Jason pushes migrations himself" (`cityhall/AGENTS.md:114`). cityhall shipped 72 migrations in the last 30 days.

### 9.4 Pros and cons

F is bureau files as the source of truth, plus a read replica. D is the DB as the source of truth.

| Criterion | F: bureau files + replica | D: DB as source | Favours |
|---|---|---|---|
| **Scale** to every US jurisdiction | about 40k small files beside 311k; prospector already ships 2k-file PRs on its own | about 400k rows, trivial | neither; size is not the constraint |
| **Fit with prospector and formal review** | the same path as codes, guides and conventions: worktree → mergein → content gates → ship PR | intake becomes the one workstream that publishes somewhere else; a prospector run would write a bureau PR *and* a DB write, with no atomicity between them | **F** |
| **Ease of changing the format** (Q1/Q2 are still open) | edit the linter and the writer in one PR | a migration that Jason applies, RLS, DB tests, a data migration, then the writer | **F** while the format moves |
| **Manual edits by Will or an agent** | Claude edits markdown, the PR shows a diff, Foreman reviews, merge; 17 of 18 v2.7 edits went this way | needs an API or editor that agents and people both use | **F** |
| **Manual edits by non-engineers** (staff, the city, a customer) | they can't edit; they ask someone to open a PR | an app editor, which doesn't exist yet and needs its own review step, or edits go live unreviewed | **D**, after building the editor |
| **How fast a fix goes live** | PR + CI (about 10 min) + merge + sync (about 3 min) | immediate | **D**, at the cost of an unreviewed change reaching live reviews |
| **Traceability** | diff, author, PR, review and blame for free; a review pins the exact content by commit | versions, an audit log and who-changed-what all have to be built (A1, A2 and A6 rebuild part of git) | **F** |
| **Automatic refresh** | a refresh is a prospector run whose output is a PR with a readable diff, merged autonomously like every other workstream | the same detection and extraction, then a DB write; the diff must be built as an app view | **F**, slightly; the hard parts don't depend on storage (§9.5) |
| **Product reads:** app pages, queries across jurisdictions, review linkage, counting, `intake_ready` | via the replica, at most one sync behind | native | neither; the replica gives the same reads |
| **Per-customer or per-project variants** (numbering maps, forced outcomes, a firm's own checks) | don't belong in a shared repo; one project and one firm already sit in Austin's version dir (A15) | tenant rows under RLS | **D** for overlays only |

### 9.5 Refresh is the same work on either store

Scaling intake means keeping about 2,000 checklists current without a person in the loop. That takes five steps, and only the last depends on where items live:

1. **Detect.** On prospector's freshness clock, re-fetch each intake source, compare its sha256 and etag with the manifest, and stop if nothing changed.
2. **Re-extract** the changed sources with intake-prospecting.
3. **Match** each regenerated item to its existing stable ID (same item, edited, split, new, or gone). This is the hard part. It needs D4's IDs and an LLM judge like the one intake-score already plans.
4. **Bump** the semver from the matched diff (A2).
5. **Publish:** a bureau PR on prospector's autonomous path (F), or a DB write plus a diff view (D).

**Proposal:** add the refresh as a sibling spec, `intake/refresh`. It is what scaling actually needs, and none of it waits on the flip.

### 9.6 When the flip would be worth it

Flip, or add DB-owned overlays, only when one of these is real:

| Trigger | Response |
|---|---|
| People who don't use git need to change checklist items routinely (weekly, across many jurisdictions) | build the app editor and flip, with an export PR to keep git history (A4 M4) |
| Customers or firms need their own variants of a jurisdiction's checklist | **overlays:** an App-DB table of per-org or per-project adjustments (numbering, forced outcomes, added or disabled items). It is `origin = 'app'`, like `jurisdiction_departments`, applied at run time. The jurisdiction checklist stays in bureau |
| A fix must reach live reviews in minutes, routinely | an overlay or override row, not the flip |

None of these is true today.

### 9.7 What this means for the other findings

| Finding | If bureau stays the source |
|---|---|
| A1 history backfill | keep, so the replica can link old reviews |
| A2 semver | keep; it lives in bureau and the runbook stamps it with no DB lookup |
| A3 files in Storage | **defer** for guide text; only the flip needs every byte in Storage. The replica stores items, plus prose only if the app shows it. **Revised by A19:** figures need Storage regardless |
| A4 the path to the flip | keep M1 (stamping); **drop M2–M4** from the plan and keep them as §9.6's triggers |
| A5 groups | keep, in bureau form: group IDs in a sidecar, with the DB tables following |
| A6 provenance | keep |
| A7 counting | keep; it reads the replica |
| A8–A17 | keep |

**Decision for Will:**
- Bureau stays the source of truth, and the flip comes off the roadmap.
- `intake/db-source-of-truth` becomes "not planned; triggers in A18".
- A new `intake/refresh` sibling replaces it.

## 10. Reference images in intake guides

**A19. Guide figures don't change A18; they sharpen it. Keep the text and the hashes in bureau and the bytes in Storage, addressed by sha256, and hydrate them into the run's guide copy at 1.4-resolve. The vision CLI attaches each figure with its caption from the guide.** *(added 2026-10-15)*

Will wants CC guides to embed reference images soon, the way the comment-resolution-check (CRC) generated guides do, and the CC vision tool to accept them, the way `crc_vision_check` does. winston#312 already sketched the vision side. Its D2 is figures addressed by id, each with its own caption; its D3 is region targeting. None of it is built yet: `bin/vision.ts` has no `--ref` or `--region`. This section settles where the images live and how they reach the run. The evidence was sampled read-only on 2026-10-15 from the Lamar + Collier CRC guides.

### 10.1 What CRC does today

- **Where they live:** bucket `crc-guides`, path `{project}/{submission}/{baseline version}/{generation}/`. For Lamar + Collier (project `23301a8a`), sets 4/0–4/6 come from the U0 MCR and checked v4–v7; sets 7/0–7/1 come from the U1 MCR and checked v8.
- **Size:** 125 figure files totalling 48.6 MB, of which **86 are unique (22.4 MB)**, because sets are copied forward byte for byte.
  - The largest set is 4/6: 33 figures, 12.2 MB.
  - 7/1 has 9 figures, 1.09 MB.
  - All are PNG. The median is 222 KB. The 600-DPI redline crops reach 4000 × 3210 px and 2 MB; MCR figures are 200–1700 px.
- **In the markdown:** only inside a guide's `## Figures` section. Each figure is a bullet `**{item ids}** — {caption} *({type})*`, then `![caption](figures/{slug}/N.png)`, a description paragraph and an optional `Constraints:` line. Captions are written by an LLM when the guide is generated. Samples:

  | Guide · item | Figure | Kind | Size |
  |---|---|---|---|
  | crc-CA-1 · CA-10 | CRZ root-zone impact thresholds | a manual's reference diagram | 938 × 851, 198 KB |
  | crc-tpw · TPW-10 | SD 440-2 bike ramp transition | city standard detail | 619 × 822, 158 KB |
  | crc-tpw · TPW-10 | Collier St bike lane markup | reviewer markup, site-specific | 1682 × 978, 136 KB |
  | crc-DE-1 · DE-6 | analysis-point runoff table | table screenshot | 639 × 225, 48 KB |
  | crc-TPW-2 · TPW-15.3 | shared-use path behind bus landing | TCM standard detail | 925 × 741, 149 KB |
  | crc-aw-redlines · AW-RL-10 | red X over SD 503S-6W | 600-DPI redline crop | 4000 × 3210, 2.0 MB |
  | crc-DE-2 · DE-31 | site plan markup | **a bad crop**: mostly whitespace | 535 × 363, 12 KB |
  | crc-PR · PR-5 | parkland dedication capture | the same crop as v7 APR-5, re-encoded | 1069 × 834, 472 KB |

- **At run time:** `fetch-crc-guides.ts` downloads the **whole** generation folder into the workspace, including a 127.5 MB redlines PDF. `crc_vision_check` resolves `referenceImages[].path` under it and sends the raw bytes (no resizing, no limit on count) after the target sheet, each labelled with **a description the agent writes at call time**. In the v8 run 2026-09-17-145517, 4 of 57 vision calls attached a reference.

### 10.2 What went wrong in CRC, and the rule that prevents it

| CRC defect (evidence) | Rule for intake |
|---|---|
| **Overwritten in place.** Set 4/6 was repaired on 2026-07-10: 12 figures added, 3 replaced, 2 removed, and the guides rewritten, all under the same paths. Runs before and after saw different figures. | Blobs are content-addressed (`<checklist>/figures/<sha256>.<ext>`) and never overwritten. A changed figure is a new hash and a PATCH (A2). |
| **No hashes anywhere.** The manifest hashes only `mcr.pdf`; the census sha1 covers embedded PDF bytes and stays local; eTags are unrecorded. | The figure manifest in bureau records `sha256`. Hydration verifies it, and `vision-log.jsonl` logs it per call (#312 D5). |
| **The caption at call time is the agent's.** The DE-30 manhole failure, and the TPW-10 descriptions in run 145517. | The CLI attaches the guide's caption; the agent may add a note but can't replace it (#312 D2). |
| **Nothing checks references against files.** `verify-phase.py` never parses `![](figures/…)`; a dangling reference shows up only as a skipped image at call time. | `lint:intake` checks that every figure reference in a guide has a manifest row, and every manifest row is referenced. CI checks that each sha256 exists in the bucket. |
| **Slugs drift between generations:** `PR5` vs `PR-5`, `SP48` vs `SP-48`, `IW/1` vs `IW-1/1`. | A figure ID is keyed to the stable item ID, `austin-0042/F1`. It survives regrouping (A5) and renaming. |
| **Fetch-everything:** a 127.5 MB PDF lands in every run. | Hydrate only the figures the manifest lists, from a local cache keyed by sha256. |
| **No resizing:** 4000 px crops go to a model that views about 1568–2000 px (#312 Q3). | Store the original. The CLI downsizes at call time to the mode's view size and logs the dimensions it sent. |
| **Duplicates:** 125 objects, 86 unique. | Content addressing dedups across versions and generations for free. |
| **Rarely used:** 4 of 57 calls. | The review prompt names the figures per item (#312 §9). |

### 10.3 Where the images live: files, DB, or Storage?

- **Not in git.** Bureau tracks **0 images and 0 PDFs** today. Codes record a source URL and a sha256 in `meta/provenance.json`, and CC source snapshots keep `sources/manifest.json` in bureau with the bytes in `cc-source-snapshots`. Figures in git would grow `.git` forever, because history can't be pruned. CRC re-extracts every figure per generation, and one Lamar guide set is 12 MB. Across about 2,000 jurisdictions that is tens of GB. Prospector's blobless sparse clone would survive it; every full clone and CI checkout would not. Git LFS would add infrastructure bureau doesn't have.
- **Not as DB rows for runtime.** The run needs bytes, and Storage serves bytes.
- **Storage, content-addressed, with the text in bureau.** This is the same split bureau already uses for snapshots, so A18 holds. It **revives part of A3**: Storage becomes required, but only for figures, not for guide text.

**The shape:**

```diff
 jurisdictions/austin/completeness-check/v2.8/
   cc-21.md                        # "## Figures": ![F1 caption](figures/austin-0042/F1.png)
+  figures.yaml                    # one row per figure (below); lint:intake checks it
   intake-ids.tsv
   version.yaml                    # A2

 Storage: intake-figures/austin/<sha256>.png        # immutable; authenticated + workflow_run read
```

```yaml
# figures.yaml
- id: austin-0042/F1            # stable: item id + figure number
  items: [austin-0042]
  caption: CRZ root-zone impact thresholds
  type: reference-design        # reference-design | site-example | table | redline
  description: >-               # what it shows and what it does NOT show
    …
  constraints: "min 50% of CRZ preserved at natural grade; …"
  sha256: 9f2c…
  media_type: image/png
  px: [938, 851]
  bytes: 197602
  derived_from:                 # optional; enables refresh (§9.5)
    snapshot: sn_tcm-3-5_20261007-ab12cd34
    page: 14
    bbox: [0.12, 0.30, 0.55, 0.62]
```

**Who writes it:**
- The author uploads the blob before the PR, as cc-source-citations' 1.2-capture already uploads snapshots with the service-role key. That author is intake-prospecting or a Will-directed session.
- The PR carries only `figures.yaml` and the markdown.
- CI checks the hashes exist in the bucket. `sync-cc-sources.yml` already holds the secrets.

**Hydration at 1.4-resolve:**
1. 1.4-resolve already copies the version dir into `$RUN/1.4-resolve/checklist/` (`cc.py:307`).
2. It then reads `figures.yaml` and fetches each sha256 from a host cache, or from the bucket on a miss.
3. It verifies each hash and writes the file to the path the markdown names.
4. It records the list in `resolved.json`.

The run then reads a self-contained guide dir, exactly as CRC's agents do. One more property falls out: `checklistsTreeHash` covers `figures.yaml`, so the git tree hash pins the image bytes transitively. A review's existing provenance identifies its figures with no new field. A8's amend comparison still has to ignore the intake-only files, but `figures.yaml` belongs in the hash.

**The vision call** (#312 D1–D5, now concrete):
- The call is `node $RUNBOOK/bin/vision.ts … --ref austin-0042/F1 [--ref …]`.
- The CLI looks the ID up in the hydrated `figures.yaml` and sends the target image, then each reference labelled with its ID, caption, description and constraints, then the question.
- It resizes each reference to the mode's view size, caps a call at 4 references, refuses an unknown ID with a reason, and logs `refs: [{id, sha256, sent_px}]`.
- Gateway mode sends the images as parts. Claude mode copies them into the child's scratch dir.

**In the DB (the replica, A18):**
- Optional rows, `intake_figures(checklist_id, version, figure_id, item_id, caption, type, sha256, storage_path, px)`, so the app can show figures. That includes noetic-48's per-jurisdiction pages (winston#316).
- The runbook never needs them.
- Storage policy: authenticated read, as `cc-source-snapshots` has. `workflow_run` read on Storage is unverified (A3), and cloud runs need it or a signed-URL step.

**Refresh (§9.5):**
- A figure with `derived_from` names the snapshot, page and box it was cut from. When step 1 of a refresh finds that the snapshot changed, the figure is re-cut and compared. A new hash is a PATCH bump.
- Site-example figures, from real submissions or redlines, have no source to refresh from. They are curated by hand, and their use needs permission (#312 Q2).

### 10.4 Does this change the recommendation?

No. A18 asked whether the DB should be the source of the checklist text; it shouldn't. Images add a binary store, and bureau already pairs text in git with bytes in Storage for every binary it uses. What A19 does change:

| | Before A19 | After A19 |
|---|---|---|
| A3 (files in Storage) | deferred | **required for figures**, not for guide text |
| A2 (semver) | figures not considered | a figure added, changed or removed is a PATCH; a figure that changes what an item checks needs a judgment call (Q-A2a) |
| A5 (groups) | — | figure IDs hang off item IDs, so regrouping never renames a figure |
| A8 (amend's tree hash) | ignore intake-only files | still ignore `intake-ids.tsv` and `version.yaml`; **`figures.yaml` stays in the hash**, because it pins the image bytes |
| A12 (citations) | — | `derived_from` lets a citation's source change trigger the figure check too |
| #312 | exploratory | P2's `figures/` folder in git becomes `figures.yaml` + Storage; `--ref` takes an ID from it |

**Decision for Will (A19):**
- Figures go in Storage, content-addressed, with `figures.yaml` in bureau and hydration at 1.4-resolve.
- #312 P2 is revised to match.
- The bucket's name and policy (`intake-figures`, or a `figures/` prefix inside `cc-source-snapshots`) is a detail for the v2 spec.
