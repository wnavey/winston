What doesn't change

Bureau stays the source of truth. The tables are a synced copy. Nothing is deleted or updated in place, and a manual edit in the DB would be overwritten by the next sync (D8).

The CC runbook reads exactly what it reads today. It globs *.md and names each TSV it uses, so no step reads intake-ids.tsv. Its 1.4-resolve step does copy the whole version dir into the run, sidecar included (§1). Inspector General's bureau_checklist_* cache is untouched too.

Files in bureau

Two new files per jurisdiction: intake.yaml says which checklist it uses, and an intake-ids.tsv beside each synced version maps every ref to a stable ID. The baseline gets its own folder outside jurisdictions/ (D1–D3).

An edit keeps an ID, a split mints new ones, and a number is never reused D4

The rules the files follow

D1 · The basis decides the checklist. formal means the jurisdiction's own checklist; none_found or inconclusive means generic, the baseline. No intake.yaml at all means no assignment, which is different from none_found.

D2 · The baseline lives at bureau/intake/baseline/, outside jurisdictions/, so the syncs that walk that folder never mistake it for a jurisdiction. It stays empty until its own sub-spec fills it.

D3 · Only versions with a sidecar sync. Austin v2.7-trimmed is backfilled now. The other 10 Austin version dirs can follow by adding their sidecars (Q1).

bureau#2112 already writes this format. The open intake-prospecting PR emits intake.yaml and intake-ids.tsv for new jurisdictions, with no linter yet, so whichever of it and P2a merges first fixes the format on main.

The tables

Four tables, all keyed by short text IDs rather than uuids: a version is ('austin', 3) and an item is ('austin', 3, 'austin-0042'). Everyone signed in can read them; only the sync writes (D6, D7).

Why a revision copies every item: one label has held several sets of content, because v2.7-trimmed was edited in place from July to October: IG's cache holds 6 distinct contents for it across 14 commits. A review can point at any revision, so nothing is updated or deleted.

The sync

On a merge to main, sync-intake.yml validates every file first, then calls intake_sync_version() once per version that has a sidecar, then upserts jurisdiction_intake. If any validation fails, nothing is written (D13).

One version is written in one transaction, and only when its hash is new D8, D10, D11

The hash covers every stored column, sorted by sort_order. Guide prose isn't stored, so editing it changes nothing (D10).
RPC
  1. Upsert the checklist rowIts name, bureau path and last commit.
  2. Is this content already stored?It looks up (checklist_id, label, content_hash).yes → write nothing more, skip to step 4, return created: false
  3. Insert a new revision and all its itemsThe revision is max(revision) + 1. It sets jurisdiction_slug on every item from the checklist. One bad item rolls back the whole version.
  4. Move the current flagIf is_current was passed, it clears the flag on the checklist's other revisions and sets it here. The sync passes it only for the folder CURRENT_VERSION names.
all four steps in one transaction; PostgREST alone would make each write its own

JSON

lint:intake fails a PR whose sidecar drifts from its guides D12

  1. filesAn intake.yaml or checklist.yaml that doesn't parse, or breaks the basis ruleone parser, shared with the sync
  2. driftThe sidecar's refs and the guide rows differ, in either directionso a PR that edits a synced guide table must update intake-ids.tsv too; this also catches completion-officer copying its stale guides over bureau's
  3. IDsA duplicate ID, a malformed one, or one without its checklist's prefix
  4. IDsAn ID at or above next_item, or a next_item lower than on mainread with git show origin/main:…
  5. IDsA derived_from from another checklist, or not lower-numbered than the item that names it

Open questions

Q1 · Backfill older Austin versions? 41 of the 60 CC reviews ran on 8 other labels, plus one labelled unknown. Not now; revisit when something needs to join old reviews to items.

Q2 · Should a review record the revision it ran against? The label alone doesn't pick one, because v2.7-trimmed has had several contents. The commit does, if the sync keeps a commit-to-revision lookup. 59 of 60 reviews record bureauCommitHash; the 19 on v2.7-trimmed span 14 commits.

Q3 · Cedar Park v1 (21 guides, 220 items, one row with an unescaped |): give it a sidecar now as a sparse second fixture, or wait for the intake-prospecting runbook to regenerate it?
