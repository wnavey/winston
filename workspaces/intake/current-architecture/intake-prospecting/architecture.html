Intake · Current architecture

The intake-prospecting runbook, as built

How bureau builds one jurisdiction's intake checklist from the documents that jurisdiction publishes: find them, snapshot them, extract items that cite exact words, audit the items, and write the checklist into bureau as one PR.

As built15 Oct 2026Source of truth: bureau/runbooks/intake-prospecting at b6349fb (bureau #2112)
Read the design spec →

Overview

One request names a jurisdiction. Seventeen steps later, bureau holds that jurisdiction's intake checklist in the db-schema format, and every item cites the exact words of a captured city document. Six steps are agent work, eight are scripts, three are gates.

What the runbook is for

  1. A checklist from the city's own documents. Intake is the check a submittal passes before anyone reviews its content: is the application signed, is the tax certificate attached, does the site plan show the fire lane. Austin calls it the Completeness Check; other cities call it acceptance, sufficiency review or administrative completeness. Noetic's CC review runs against a per-jurisdiction checklist of those items, and until now the only one was Austin's, built by hand. This runbook builds one for any jurisdiction, from what that jurisdiction publishes.
  2. Every item traces to words on a page. Each document is captured as a snapshot before anyone reads it for items: a PDF, page images, and every word numbered (p2w188 is word 188 on page 2). An item exists only if it cites a run of those word ids on an intake form or submittal checklist. The agent picks words; a script computes the boxes and throws out any quote it cannot find.
  3. It never sees an answer key. No session may read any jurisdiction's existing checklist, Austin's included, or any earlier Noetic intake work. Without that bar, a run scored against Austin would be scoring a copy of its own answer. The fence tab shows the four layers that hold it.
  4. Most of the machinery is borrowed. The session loop, the research ledger, the audit prompt and the disposition ruling are prospector's, read unchanged from the bureau checkout. Snapshots, word ids and quote checks come from runbooks/lib/sources, the library this PR moved out of cc-source-citations. What is new is the intake logic: the source types, the basis decision, the extraction rules, verify, and the writer.

Two places hold a run's state. The run dir is conductor's folder for one run: every step writes its outputs into its own subfolder (1.3-capture/, 2.3-verify/, …), and later steps read them. It is local and is deleted when the run is archived. The bureau worktree is a git clone of bureau that 1.0 makes inside the run dir, on a branch named intake-prospecting/<slug>-<run>. Only four things are ever written there: the research ledger, its notes.md, the checklist folder and intake.yaml. Each is committed the moment it is written, so the branch carries the run's whole history even after the run dir is gone, and it is the branch that becomes the PR.

Why a worktree from the very first step. prospector's session loop, ledger rules, audit prompt and disposition script all expect one: they read worktree.json, commit to it, and check that nothing moved under the audit. Making it first let this runbook use those tools unchanged.

The gates. A gate is a step with no runner: conductor stops there (exit 75) until a decision file is written. The request sets gates: human or gates: auto. Under auto, the gate's own contract records decided_by: auto and passes, which is how all the Austin loop runs went end to end unattended. Publishing needs a person: publish: true with gates: auto is refused at 0-request.

Finding the documents

Steps 0 to 1.5 turn a jurisdiction's name into a short list of captured documents and a decision about which of them define intake. Only two of the seven steps are agent work, and only one of those touches the live web.

Three setup steps spend no tokens: a request, a worktree, and a list of leads steps/0-request … 1.1-inputs

  1. gate · the operator0-requestWrites request.json: the jurisdiction (slug, name, state; it need not exist in bureau yet), an optional application-type hint, optional seed URLs, gates, publish, replace and who asked. A prospector wrapper can pass a worktree it already owns.
  2. script · ip.py worktree1.0-worktreeA blobless, sparse clone of bureau from origin/main onto intake-prospecting/<slug>-<run>. Writes seeds.json, each tagged with where it came from. A jurisdiction prospector never touched starts from the web.

Why discovery is a loop of sessions. Finding every intake document a city publishes can outrun one context window, so 1.2 uses prospector's step loop: each launch is a fresh session that reads what earlier sessions left (their reports, logs, the ledger and notes.md), does about an hour and $60 of work, and ends with a report whose status is done, continue or blocked. continue exits 100 and conductor launches the next session, up to eight. The research runner is Opus 5.5 at high effort with a three-hour backstop per session.

The scope gate shows a person 1.4-classify/readout.md: the sources table, the basis with its quoted evidence, the scope sources, where the classifier disagreed with discovery's typing, and a ## Need you? list. The person approves, or revises with edits (add or remove scope sources, retype a source, override the basis), and 1.4 re-runs with the edits and answers them in a ## Revision section.

Extracting the items

The approved scope pages are divided into groups, one fresh worker per group writes items that cite word ids, a script verifies and deduplicates them, and a reviewer that never saw the workers audits the result. Charges send back only the groups they name, at most three times.

Groups follow the city's own instrument. 2.1 reads every scope page and divides them into groups of 2 to 12 pages, one worker each, keyed cc-1, cc-2, … in the instrument's order. The ordering rule is the instrument's own sections; failing that, the reviewing department; never another jurisdiction's group list. Every page of every scope source belongs to exactly one group (the contract blocks on this). Pages of different instruments that list the same submittal items go to one group, so one worker writes each requirement once and cites every instrument; that rule came from Austin, where the application form, the intake checklist and an arborist addendum all list the same documents. Each group also gets a supporting list: the code sections or manuals its pages refer to, which a worker may cite beside a scope citation but never instead of one.

The audit. 2.4 is prospector's audit.md with this runbook's paths substituted, run as a fresh Opus session at high effort. It reads the verified items, the coverage map and the snapshots, and is told never to open 2.2-extract/, the workers' account of themselves. It attacks coverage first (every uncovered page that states a requirement), then charges by kind: scope (compliance rather than completeness, or a citation that doesn't state the item), coverage, checkability (needs a site visit or the city's records), duplicate and format. Each claim opens with the group files it concerns, which is how disposition knows which workers to wake. Unconfirmed suspicions go in leads, not charges. Later rounds are frozen in scope: they re-judge earlier charges and charge only regressions.

The revise round. A woken worker sees the round's findings and must answer every charge naming its group in a ## Charges table in notes.md, as ADDRESSED or SCORED_BELOW_BAR; its contract fails until it does. Duplicates resolve by rule, not by rewording: the higher-numbered group drops its copy and the lower one keeps it and adds the other instrument's citation. On Austin, round 1 carried between 35 and 82 charges, mostly duplicates, and the run went clean in two to four more rounds. Those duplicate charges are the main cost lever left.

3.1 is the router. Gates can only wait, so a review that says revise is acted on by the next step that runs: 3.1. When 4.1-review/decision.json says revise, 3.1 writes a void-request.json and exits 1. With groups named in regroup, those groups go back through 2.2 extraction (and verify, audit and prose after them); with none, only 3.0 prose is rewritten. The prose writers (Opus 5.5, medium) each write one prose.json: a description, an overview of the requirements in the city's terms, the documents to review, method notes where "complete" needs a definition, and at least two common rejection triggers. Their contract keeps the runbook's own vocabulary (step, gate, round, contract) out of client-facing text.

The fence

Rule 19: no session may read any jurisdiction's existing checklist, or any earlier Noetic work about intake. A prompt saying so is not enough, so four layers hold it, from "the file is not on disk" down to "the step fails if a tool call touched it".

  1. The folder is not on disk. 1.0's sparse checkout excludes jurisdictions/<slug>/completeness-check/ and checks out no other city at all, so a recursive grep of the worktree that names no barred path still cannot find a checklist.
  2. The workers hold no checkout. Extraction and prose workers get no tools: [bureau], so they have no $BUREAU; the charge-answer rules they need were copied into lib/charges.ts so their contracts run without it.
  3. Every prompt states the bar as a capability. "You may not read any jurisdiction's existing completeness checklist…", never "avoid this folder" (which would tell a session where to look). Sessions that hold $BUREAU search with --exclude-dir=examples --exclude-dir=completeness-check --exclude-dir=intake-score.
  4. The tripwire. Each agent step's contract scans its session logs ($RUN/.logs/<node>.*.jsonl) for barred paths in the path-shaped fields of tool calls (file paths, commands, URLs, globs): any completeness-check/, completion-officer/, intake-score/scenarios/, a runbook's examples/, /_eval/, review_comments, Inspector General reports. A hit fails the step. Text a session writes, or a sub-agent prompt stating the bar, is not a read; austin-r1 failed on exactly those false positives before the scan was narrowed.

How a run is scored

intake-score is a second runbook that grades a finished run against Austin's hand-built checklist (v2-trimmed, 190 items). It sits outside the fence, and it is how the Austin loop tuned the prompts over 19 runs.

Blind judges score recall and precision in parallel, each verdict cached by content hash intake-score/runbook.yaml

main pathstacked box = one judge per packet, in parallelblack diamond = gate
gate0 request
script1.1 inputsM1, M2, M6; judge packets

1.1 builds the reference from bureau's guides at the commits expected.yaml pins, computes the mechanical metrics from the run dir, and writes judge packets only for cache misses, so re-scoring an unchanged pair spends nothing. Recall judges see one reference group and the candidate items and rule each reference item match, partial or none. Precision judges see one candidate group and rule each item an intake item, compliance, and traced to its quote. Judges are Opus 5.5 at medium effort.
