Parcel-Geo-Location Resolution — Architecture

How the parcel-geo-location-resolution skill turns any one of address · lat/lon · parcel-ID into a coherent, traceable address + lat/lon + parcel-set triple — and the geometry artifacts (parcel-rings.geojson, subject-boundary-overlay.png) every downstream visual read must frame from. This is a how-it-works map: the seven steps, the call sequence, and the fail-fast guards that make it a deterministic input rather than free-form agent reasoning.

Tab 1What it does & why

One job: resolve a property's location triple — address, lat/lon, and parcel-ID(s) — as a coherent, independently-validatable artifact, accepting any one of the three as the primary input. The most common path is address in → parcel-ID + lat/lon out. It either produces a high-confidence resolution or it produces nothing.

the one-line answer The skill runs 7 steps — jurisdiction detection → primary parcel lookup → customer-input reconciliation → two-layer multi-parcel detection → mandatory geometry & boundary overlay → write the standardized location-resolution.md → (the MCP-call log writes itself). Its headline output, parcel-rings.geojson, plus the rendered subject-boundary-overlay.png, exist so every downstream imagery read frames the subject from a drawn boundary — never from a bare address pin that may sit on a neighbor's land.

2The four failure modes it exists to kill

Subject-location resolution is structurally fragile when it lives as free-form agent reasoning inside a larger pipeline. Pulling it into its own skill kills four recurring failures:

Customer identifiers get lost
  • A caller passes PIN# 17 00950004067 but the manifest only has a {lat,lon} slot → the ID silently drops to null.
  • Fix: reconcile the customer-pin as a tagged union; STOP on material disagreement.
One-to-one lookups assert single-parcel
  • An address-driven tool can only ever return one row — but a site assembled from 3 parcels still has one street address.
  • Fix: an always-on adjoining-parcels GIS sweep + a concept-plan vision pass.
Tool calls aren't structurally logged
  • Free-form reasoning leaves only a prose summary that can mis-attribute which source produced which value.
  • Fix: producer-owned JSONL — the Surveyor MCP server logs every call in real time.
“Data-gap” is treated as “stop”
  • Drawn area > assessor acreage by >15% is an assemblage signal, not a footnote — but shipping it as a later flag bakes a wrong “single-parcel” premise into every acreage-keyed calc.
  • Fix: the 15% block threshold hard-STOPs.

Tab 2Inside the resolve — how the triple gets built

This is the box you asked about: the Skill agent · parcel-geo resolve. Its whole job is to turn one input into a coherent address + lat/lon + parcel-ID + rings quad. The mechanic is a funnel: three input types each resolve, by a different first call, down to a single parcel-ID — and then every path makes the same second call — <src>_parcel_details(parcelId) (the source-prefixed details tool) — which is the one source that emits the canonical centroid and the polygon geometry. Route to an ID, then let parcel_details back-fill the rest.

the linchpin — read this first <src>_parcel_details(parcelId) is called on all three paths and is where the triple actually becomes coherent. Its returned WGS84 centroid becomes the canonical lat/lon — not the caller's input coordinate and not the Census geocode (both are approximate; the centroid is parcel-exact). Its returned polygon becomes the rings. So the “how” is: the input only ever gets you to a parcel-ID; the parcel-ID is what unlocks the precise lat/lon and the geometry.

2The four facets — where each comes from

The triple is really a quad. Read this as: the input gives you one facet for free; the first call gets you the parcel-ID; the second call (parcel_details) gets you the other two, precisely.

why the second call is non-negotiable Even when the input is a parcel-ID (compartment ③), the skill still calls parcel_details — both to confirm the jurisdiction (a hit proves the PIN belongs to that assessor) and to obtain the centroid + polygon that no other call returns. A one-row assessor_search result proves an address matched a record; it does not prove single-parcel scope, and it does not carry geometry. That's why routing-to-an-ID and then always calling parcel_details is the whole shape of the resolve.

3A note on the tool names — the <src> prefix

the names are schematic — there is no fixed <jur>_ convention Across the 56 jurisdictions and ~480 registered tools, <src> is the data source (a CAD / assessor / county-GIS system), which is usually not the jurisdiction slug: Dallas is dcad_search / dcad_details, Charlotte NC is mecklenburg_*, West Sacramento is yolo_* (Yolo County), Broward is bcpa_*. The verbs vary too (_search / _cad_search / _assessor_search; the details step is often _property_profile, not _parcel_details), the lat/lon path has no standard by-point tool (some fold it into the search tool as a byPoint arg; some have none), and a single jurisdiction can expose several source prefixes at once — atlanta-ga is fulton_* + dekalb_* + atlanta_* (two counties + city GIS). What is invariant is the shape, not the names: search/resolve → ParcelID, then a details call that returns polygon geometry + WGS84 centroid. The agent binds the real names at runtime from each jurisdiction's surveyor/jurisdictions/<slug>.md “Your Tools” table.

1The two-independent-confirmations rule

The one design principle that governs Step 4: a parcel joins the resolved set only when two independent sources agree. A single signal — shared owner, a title-block ID, a smoking-gun callout — makes a candidate, not a member. Everything short of two confirmations flows to Open Questions for human-in-the-loop confirmation, with a property-profile URL so the human can verify fast.

Step 4 — two-layer multi-parcel detection
4Multi-parcel detection (4a always · 4b/4c if concept plan)agentopus 4.7 vision

4a — adjoining-parcels GIS sweep (always on). Buffer the primary polygon ~50 ft, query the parcel layer for intersecting polygons, score each candidate (shared owner = high, shared subdivision = medium, shared use-code = low). Candidates are never auto-included — the sweep surfaces them for confirmation. Every adjoiner is recorded in adjoining-parcels.json for the audit trail.

4b — concept-plan vision (when --concept-plan supplied). pdftoppm renders the PDF at 300 + 600 DPI, magick quadrant-crops it, and a scoped Opus 4.7 native vision pass reads the title block (declared parcel IDs, total area), the drawn boundary, and smoking-gun callouts (“Tract A/B”, “interior lot lines to be abandoned”, multiple plat refs). Findings are cross-checked against 4a's set; auto-inclusion only when title-block evidence and the GIS sweep agree and vision confidence is high.

4c — 15% block threshold. Δ = (declared_area − resolved_set_area) / resolved_set_area.

Auto-include
only on two independent confirmations (see the rule box above); one signal ⇒ Open Question
Outputs
adjoining-parcels.json · concept-plan-extracted/ (renders, crops, concept-plan-data.md)
STOP
stop Δ > 15% ⇒ stopped:assemblage-suspected
Deferred
three-way Google Maps + cadastral GIS reconciliation, and agent-browser point-sampling — surfaced as Open Questions in v1
Step 5–7 — geometry, artifact, log
5Parcel geometry & boundary overlayscriptMANDATORY

Persist the resolved ring(s) and render a boundary-overlaid aerial so every downstream visual read starts from a frame where the subject is unambiguous — and mechanically flag parcels whose centroid/pin does not sit inside them. This is the step that would have caught incident #10.

Persist
write polygon geometry from Step 2's parcel_details (held in context since Step 2) to parcel-rings.geojson. If the tool omitted geometry, fetch it directly — one keyless ArcGIS query (returnGeometry=true&outSR=4326). Never soft-skip.
Scope
the file holds the in-scope resolved set only — the primary parcel plus any parcels Step 4 auto-included via two-independent-confirmations. Adjoining/adjacent candidates are excluded (they live in adjoining-parcels.json + Open Questions); the overlay strokes only these resolved rings. Despite the plural name, it's “the subject,” not “every ring nearby.”
Render
scripts/render_boundary_overlay.py fetches an ESRI World Imagery frame (keyless), strokes every ring in orange with its parcel ID, marks the geocode pin, emits geometry-summary.json
Flags
centroid_inside_ring / pin_inside_ring — a false means the parcel is non-convex; copy the warning verbatim and frame all imagery from the overlay. A false flag is a warning, not a stop.
Cross-check
ring area vs assessor acreage — > 15% disagreement ⇒ wrong-ring signal, re-check ID/layer
6Write location-resolution.mdagentthe artifact

Produce the standardized artifact in <output-dir>/location-resolution.md — nine sections in a fixed order: header (with status), Confirmed Subject Location, Parcel Set, Parcel Geometry, Customer-Supplied Inputs, Methodology, Assumptions, Tool-Call Log, Open Questions. When status != completed, it also carries a “Reason for incomplete resolution” + “Recommended caller action” section.

Exit
0 on completed / completed-with-warnings:*; non-zero on every stop/fail
7MCP-call log — already writtenproducer-ownedno write step

The Surveyor MCP server logs every tool call to location-resolution-mcp-calls.jsonl in real time as the skill runs — no separate write step. The path is chosen at server startup (the NOETIC_PHASE_LOG env from Step 2 wins), and Step 6 records the actual path from the startup banner. The JSONL is byte-compatible with the surveyor's intermediate/research-findings.jsonl; one reader serves both.

1Census geographies⇢ county · normalized addr · lat/lon · FIPS
API
http keyless geocoding.geo.census.gov/geocoder/geographies/onelineaddress (coordinates path for a lat/lon input) with benchmark=Public_AR_Current&vintage=Current_Current. Skipped entirely when --jurisdiction is passed.
Returns
the matched address block: { matchedAddress · coordinates{x,y} · geographies.Counties[0]{NAME,STATE,COUNTY} }. County name drives the surveyor_slug match; the normalized address + lat/lon feed the methodology block.
Example

    "NAME": "Fulton County", "STATE": "13", "COUNTY": "121" }] }
}]  // → surveyor_slug: atlanta-ga
2<src>_assessor_search⇢ best-match parcel row
API
mcp fulton_assessor_search(query, searchType="address") — the prefix is the data source (Fulton County GIS), not the jurisdiction slug atlanta-ga (which also exposes dekalb_* and atlanta_* tools). The address is normalized first (drop everything after the first comma) because Fulton CAMA stores the street portion only and implements WHERE UPPER(Address) LIKE '%query%'.
Returns
[{ ParcelID, Owner, Address, ... }] — best-match first; one row in the single-parcel case. A one-to-one result does not prove a single-parcel site.
Guard
A zero-row result ⇒ failed:address-not-found. The skill never fuzzy-broadens (strip unit, partial match) — a near-match can resolve to a completely different parcel.
Example
// normalized query: "4279 Roswell Rd NE"
[{ "ParcelID": "17 009500040675",
   "Owner": "IRT PROPERTY COMPANY",
   "Address": "4279 ROSWELL RD NE" }]
3<src>_parcel_details⇢ canonical record + polygon + centroid
API
mcp fulton_parcel_details(parcelId) — always called after the input-shape-specific call to capture the full record. The returned centroid becomes the canonical lat/lon for every downstream artifact.
Returns
{ ParcelID · Owner · LandAcres · geometry(rings) · centroid{lat,lon} · attributes{...} }. The geometry is what Step 5 persists to parcel-rings.geojson.
Example
{ "ParcelID": "17 009500040675",
  "LandAcres": 7.38,
  "centroid": { "lat": 33.871083, "lon": -84.379667 },
  "geometry": { "rings": [[ [-84.3801,33.8715], … ]] } }
4adjoining-parcels GIS sweep⇢ scored candidates (never auto-included)
API
http keyless ArcGIS query?geometry=<buffered ring>&geometryType=esriGeometryPolygon&spatialRel=esriSpatialRelIntersects against the jurisdiction's parcel layer.
Returns
every intersecting parcel with ParcelID · Owner · Acreage · LandUseCode · Subdivision. Scored: shared owner = high, shared subdivision = medium, shared use-code = low. Written to adjoining-parcels.json.
Rule
Candidates are never auto-included from this signal alone. Auto-inclusion needs a second independent confirmation (a title-block ID from the vision pass). Otherwise → Open Questions with a property-profile URL.
5scoped Opus 4.7 vision⇢ concept-plan-data.md + confidence
API
llm Opus 4.7 native vision over the 300/600 DPI renders + quadrant crops. Runs only when --concept-plan is supplied. Scoped to multi-parcel signals only — not a full-feature extraction.
Returns
concept-plan-data.md: title-block parcel IDs, declared total area, recorded-plat refs, drawn-boundary shape, smoking-gun callouts (Tract A/B · abandoned lot lines · UDP · multiple plats), plus an overall confidence { high | med | low }.
Gate
Auto-inclusion of any parcel requires overall confidence high and corroboration from the 4a GIS sweep. Confidence low ⇒ every finding becomes an Open Question (completed-with-warnings:vision-pass-low-confidence).
6render_boundary_overlay.py⇢ overlay.png + inside-ring flags
API
http + local — fetches a keyless ESRI World Imagery frame via curl, strokes every resolved ring (orange, labeled with parcel ID), marks the geocode pin, computes geometry.
Returns
subject-boundary-overlay.png + geometry-summary.json: per-parcel vertex count, bbox (ft), ring area (acres), and the two mechanical flags centroid_inside_ring / pin_inside_ring.
Warn
A false flag means the parcel is non-convex — any point-centered image shows a different property at its center. Copy the warning verbatim; every downstream visual read frames from the overlay. This is a warning, not a stop.
Example
{ "parcels": [{ "parcel_id": "17 009500040675",
    "vertices": 34, "area_acres": 7.36,
    "centroid_inside_ring": true,
    "pin_inside_ring": true }] }
