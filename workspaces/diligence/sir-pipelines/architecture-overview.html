2How a step executes — the runner

Steps are declared in pipeline.yaml (conductor's workflow.yaml vocabulary + runner: claude-session and per-step hitl:). Conductor sandboxes cannot pause for a human, so these deliberately run outside conductor.

  • Step kinds: script · agent · checkpoint (only a human --decision closes a checkpoint).
  • Commands: validate | list | run --step <id> | verify | checkpoint. run executes one step's entrypoint on one model: tier and stops at its gate.
  • Lineage: requires: is enforced; a cost_band triggers a soft cost check-in; skip_when supports exactly one predicate (empty_array).
  • Where it runs: ~/noetic/working/sir/{customer}/{project}/{ts}/, subscription tokens.
the design win Because state is on disk and every step is re-runnable + verifiable, a correction is a targeted re-run — not a full re-generation. The pilot's entire §5 was re-run as a controlled experiment over the same §1–§4 artifacts, and every prior render was preserved under _superseded-*.

6SIR pipeline steps in detail

One card per step, sourced from bureau/pipelines/sir/ — its prompt(s), the Python it runs (helpers vs. check_*.py verifiers), any external claude-plugins skill or separate-repo CLI it delegates to, its load-bearing outputs, and how its gate is enforced. A step is one of three kinds — agent (spec-and-verify: the runner prints the spec, a Task agent does the work, verify checks the outputs), script (a deterministic entrypoint the runner just runs), and checkpoint (executes nothing; a human --decision is the only thing that closes it).

the shared verification contract Nearly every agent step wraps deterministic tools and its check_*.py verifier. The runner never infers health from prose — it asserts each tool's own recorded verdict via health_requires:, so a polished file at full size still fails the step if the tool behind it fell back. Several verifiers double as index builders (--write-index / --write-report): the machine-readable seam a downstream step consumes is derived from the markdown, never hand-authored beside it, because two copies of the same findings drift and the drift always favours the summary.

6aStep timing — a worked example

Every executing step already stamps its own start and end into the append-only event ledger at state/events.jsonl: run writes step.recorded status=running before it hands off, and verify writes status=complete (or failed) after the outputs are asserted. So per-step latency is a read-time derivation over data we already emit — no new instrumentation, no sidecar, one appended JSON line per transition. The method: pair each step's running with its next event for that same step, and sum those segments. Two things fall out for free:

  • Between-step idle is excluded. The gap from one step's complete to the next step's running — an operator reading a readout, going to lunch, or picking the run back up after the weekend — lands between pairs and is never counted against any step.
  • Gate human-wait is structurally separated. The two hard stops (3.2, 4.4) plus the publish gate (5.8) are checkpoint steps that emit awaiting-decision, never running — so pairing skips them, and their operator wait is read off presented_at → decided_at instead. Human decision time never inflates agent time.

two blind spots the free method keeps The ledger is "good enough" today for triage, but two categories of time hide inside a step and cannot be separated from two events alone. 3parcel-geo-location-resolution⇂ location triple · rings · geometry

parcel-geo was shorthand — the skill's real name is parcel-geo-location-resolution, and it is not one call: it runs an ordered pipeline of discrete calls. Some drive the Surveyor MCP server (tool prefix louisville_); others are keyless HTTP (curl) to the Census geocoder and ESRI imagery. There is no generic-geocoder fallback — an unresolvable jurisdiction STOPs. In the pilot the operator pin landed on the adjacent Wawa; calls 3–4 are what recovered the two vacant subject pads. Each call below leads with a plain-English summary.

generic protocol, jurisdiction-specific endpoints The raw ArcGIS calls below (the LOJIC parcel queries, the ESRI export) use the universal Esri REST query grammar — but the endpoint, layer IDs and field names (gis.lojic.org/…/OpenDataPVA/MapServer/1, PARCELID, LRSN) are Louisville-specific; you only know how to build them because call 1 resolved the jurisdiction. Another county sits on a different host with different layer IDs and may call the id PIN or PARCEL_ID. That is the whole point of the surveyor tools: they normalize wildly heterogeneous county sources (ArcGIS, Socrata, scrapers, paid vendors, PDF-only) behind one uniform interface, so the pipeline is identical across jurisdictions and only the surveyor module changes. Louisville can drop to a raw curl only because it exposes a clean public ArcGIS estate — the exception, not the rule; most jurisdictions have no equivalent raw endpoint at all.

Does composition lean on the orchestrator's memory? No — and that is the whole design.

This is the sharpest way the pipeline departs from the production diligence-report skill. The skill threads Phases 0→5 through one long orchestrator context — the composer at the end has "seen" everything that came before, and that living memory is load-bearing (and lossy: the serial appendix pass literally ran out of context mid-step and needed an operator /compact). The pipeline inverts it:

  • 5.1 is an agent step — pipeline_runner.py prints the spec (5.1-compose.md) and spawns a fresh Task agent whose entire world is that spec + the run dir. There is no upstream conversation to inherit.
  • The prompt makes it a rule: "You never self-authorize past your own step" and "read the seam first and read it whole." State is the disk, not the thread.
  • The appendix fan-out hardens it further: each of the ~19 Part workers is handed a byte-verbatim persisted brief (_spawn/part-<L>-brief.md) — 4.1's rule that "an unpersisted wrapper is the one part of a spawn nobody can audit." Nothing an orchestrator merely remembers can leak into a worker; if it is not written to the brief, the worker never sees it.

The only orchestrator-held state that matters is what the composing agent itself builds within 5.1 — the fixed Part roster and the body it writes while workers run — and that is regenerated deterministically from appendix_fanout.py roster, not carried in from §1–§4.

so — could a brand-new session compose just as well from only the §1–§4 outputs? Yes for the run data — and it was proven. The pilot's entire §5 was re-run cold as a controlled experiment over the same §1–§4 artifacts, and produced an equivalent deliverable (prior renders preserved under _superseded-*). A cold composer that reads synthesis-index.json whole and reaches into the prose behind each entry has, by construction, everything a warm one had — because 4.2 was required to write it all down and the seam is derived so it cannot lie about the markdown.

Two honest caveats, and both are deliberate boundaries, not gaps:
① "only the produced artifacts" is not quite the whole input — a cold session also needs the pipeline code (the 5.1 prompt, appendix_fanout.py, check_compose.py) and the external v9 format spec at $NOETIC_SKILLS_DIR. Given {run tree + pipeline repo + skills dir} it performs identically; that triple is the contract.
② The one thing a cold start cannot recover is an operator instruction that was spoken but never written to state/hitl/. That is exactly why the 4.4 gate persists gate-4.4.json + ledger.md: to force every condition onto disk. An unrecorded verbal condition is the sole failure mode — and the pipeline's answer to it is "record it at the gate," not "keep it in the orchestrator's head."
