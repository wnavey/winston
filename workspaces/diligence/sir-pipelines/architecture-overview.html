SIR Pipelines — Architecture Overview

Two ways to produce a Site Intelligence Report: the production diligence-report skill that serves customers today, and the new bureau SIR pipeline Jason has been building to replace it. This is an orientation map — how each works, how complete the new one is, how it uses the Mayor, and what is committed to a repo vs. still living as workspace WIP.

Draft v1 · 2026-07-31 · exploratory · click a tab ↓

Tab 1The two systems at a glance

Same deliverable, same 10 disciplines, same rendering stack — but a different shape. The skill is one long orchestrator session; the pipeline is a chain of small, resumable, individually-verified steps. The new pipeline is not a branch of the skill — it is a ground-up rebuild that intends to retire it.

the one-line answer The new "SIR pipeline" is real, merged code in the bureau repo (on main, 121 files) that has already run end-to-end once to a delivered 307-page PDF. The temp dir Jason shared is his planning workspace (READMEs, PLAN/FACTS, session logs) — not the pipeline itself. Almost nothing of substance is stranded in the temp dir; the engine is in the repo.

1Side-by-side on the dimensions that matter

Form & where it lives

diligence-report skillexisting
  • A single Claude Code skill — one big SKILL.md orchestrator + ~34 prompt files + 26 reference docs.
  • Lives in claude-plugins/plugins/noetic-tools/skills/diligence-report/.
  • Invoked directly (Skill tool / interactive session, or the field-agent headless runner).
SIR bureau pipelinenew
  • A declarative pipeline.yaml (19 steps, §1–§7) + per-step prompts + per-step check scripts.
  • Lives in bureau/pipelines/sir/ (bureau is its own nested git repo).
  • Driven step-by-step by pipelines/lib/pipeline_runner.py, executed by a Claude Code session.

Execution model & resumability

diligence-report skillexisting
  • One long orchestrator thread runs Phases 0→5, fanning out sub-agents at Phase 2 and Phase 3.
  • State is the working directory; no formal step lineage or per-step re-run contract.
  • HITL pauses (2.5, 4.5) are gates inside the orchestration.
SIR bureau pipelinenew
  • Each step runs on its own, writes an on-disk folder + _health.json, and is independently re-runnable.
  • requires: lineage enforced; verify re-checks a step against its own outputs.
  • HITL1 (3.2) and HITL2 (4.4) are first-class checkpoint steps only a human --decision closes.

Billing & models

diligence-report skillexisting
  • Metered — Opus 4.7 + Gemini 3.1 Pro via the AI gateway (real-dollar spend).
  • Sub-agent models are not pinned in-prompt (a documented hazard).
SIR bureau pipelinenew
  • Subscription-first — Opus for judgment, Sonnet for chores; model named explicitly at every spawn.
  • The only metered exceptions: 2.1 plan-extraction still uses Gemini dual-vision (a parked question), and surveyor's declared mixed use.

Provenance & verification

diligence-report skillexisting
  • A large scrub-pass (~100 KB, 26+ numbered checks) enforces output hygiene at the end.
  • Corrections handled ad hoc; rules accreted reactively from an incident log.
SIR bureau pipelinenew
  • Per-step check_*.py scripts + _health.json verdicts; a verify gate per step.
  • Corrections are patch-never-wipe: _superseded-* snapshots + a corrections[] ledger + a diff audit trail.
  • Adversarial review is build-phase scaffolding (one Fable reviewer per newly-built step), not a runtime layer.

Maturity

diligence-report skillexisting
  • Production. This is what generates customer SIRs right now.
  • Actively hardened through end of July 2026 (latest PR #171).
  • Bloated and reactive, but battle-tested across many real runs.
SIR bureau pipelinenew
  • Pilot. Ran end-to-end once (Circle-K / Odessa TX) → 307-page PDF + DOCX.
  • §5 proven on a real render; §1–§4 verified against the pilot's artifacts but not re-run step-by-step.
  • Revision (6.1) and Learnback (7.x) not built yet.

2Where the Mayor fits — and where it doesn't

4Output

One deliverable, dual-format: site-intelligence-report.pdf (~180–340 pp) + .docx, both from one pages.tsx rendered in RDS Report mode — exec summary + structured body (+ §10 Concept Plan Review if a plan was supplied) + an in-document Research Appendix. The separate appendix PDF is retired.

2How a step executes — the runner

Steps are declared in pipeline.yaml (conductor's workflow.yaml vocabulary + runner: claude-session and per-step hitl:). Conductor sandboxes cannot pause for a human, so these deliberately run outside conductor.

  • Step kinds: script · agent · checkpoint (only a human --decision closes a checkpoint).
  • Commands: validate | list | run --step <id> | verify | checkpoint. run executes one step's entrypoint on one model: tier and stops at its gate.
  • Lineage: requires: is enforced; a cost_band triggers a soft cost check-in; skip_when supports exactly one predicate (empty_array).
  • Where it runs: ~/noetic/working/sir/{customer}/{project}/{ts}/, subscription tokens.
the design win Because state is on disk and every step is re-runnable + verifiable, a correction is a targeted re-run — not a full re-generation. The pilot's entire §5 was re-run as a controlled experiment over the same §1–§4 artifacts, and every prior render was preserved under _superseded-*.

4What the pipeline gets right that the skill doesn't

Provenance is mechanical
  • Patch-never-wipe: _superseded-* + corrections[] + a diff audit trail; the client never sees the sausage-making.
  • Per-step check_*.py + _health.json catch classes of defect a final scrub can't.
Resumable & cheap to iterate
  • Re-run one step, not the whole run; per-step timing is stamped in state/events.jsonl.
  • Subscription-billed — the pilot ran at metered_usd: 0 (except the parked Gemini 2.1 and surveyor exceptions).

5Known debt & open threads (from the PLAN)

  • Length is the headline defect: the pilot appendix ran ~3.26× both reference reports — a "write each fact once / point-don't-quote" problem, and the reserved fact-ledger follow-up is aimed straight at it.
  • Efficiency target unmet: §1–§5 ≈ 8.2 h against a 2 h goal; the fix is fanning out the serial steps (5.1 compose, 5.4 layout scrub), sequenced after the format work.
  • A few RDS / check-script defects recorded not fixed (rollup double-count, layout sampling floor, no PDF bookmarks).
  • Cutover checklist (Jason's): migrate parcel-geo + _shared-research into the pipeline, el/eptp rename + real electrical guides, surveyor → its own sub-pipeline, then retire the skill.
relationship to "New Review" The sibling bureau/pipelines/review/ reuses this pipeline's §1.2/§3.1/§3.2/§3.3/§3.4 front-end (two files are literal symlinks into sir/) and imports sir/lib/ for rendering. Improvements to the shared runner/lib and the front-end steps benefit both.
