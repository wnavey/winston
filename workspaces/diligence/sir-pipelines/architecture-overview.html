SIR Pipelines — Architecture Overview

Two ways to produce a Site Intelligence Report: the production diligence-report skill that serves customers today, and the new bureau SIR pipeline Jason has been building to replace it. This is an orientation map — how each works, how complete the new one is, how it uses the Mayor, and what is committed to a repo vs. still living as workspace WIP.

Draft v2 · 2026-08-03 · exploratory · + per-step detail (Tab 3 · §6) · click a tab ↓

Tab 1The two systems at a glance

Same deliverable, same 10 disciplines, same rendering stack — but a different shape. The skill is one long orchestrator session; the pipeline is a chain of small, resumable, individually-verified steps. The new pipeline is not a branch of the skill — it is a ground-up rebuild that intends to retire it.

the one-line answer The new "SIR pipeline" is real, merged code in the bureau repo (on main, 121 files) that has already run end-to-end once to a delivered 307-page PDF. The temp dir Jason shared is his planning workspace (READMEs, PLAN/FACTS, session logs) — not the pipeline itself. Almost nothing of substance is stranded in the temp dir; the engine is in the repo.

2How a step executes — the runner

Steps are declared in pipeline.yaml (conductor's workflow.yaml vocabulary + runner: claude-session and per-step hitl:). Conductor sandboxes cannot pause for a human, so these deliberately run outside conductor.

  • Step kinds: script · agent · checkpoint (only a human --decision closes a checkpoint).
  • Commands: validate | list | run --step <id> | verify | checkpoint. run executes one step's entrypoint on one model: tier and stops at its gate.
  • Lineage: requires: is enforced; a cost_band triggers a soft cost check-in; skip_when supports exactly one predicate (empty_array).
  • Where it runs: ~/noetic/working/sir/{customer}/{project}/{ts}/, subscription tokens.
the design win Because state is on disk and every step is re-runnable + verifiable, a correction is a targeted re-run — not a full re-generation. The pilot's entire §5 was re-run as a controlled experiment over the same §1–§4 artifacts, and every prior render was preserved under _superseded-*.

6SIR pipeline steps in detail

One card per step, sourced from bureau/pipelines/sir/ — its prompt(s), the Python it runs (helpers vs. check_*.py verifiers), any external claude-plugins skill or separate-repo CLI it delegates to, its load-bearing outputs, and how its gate is enforced. A step is one of three kinds — agent (spec-and-verify: the runner prints the spec, a Task agent does the work, verify checks the outputs), script (a deterministic entrypoint the runner just runs), and checkpoint (executes nothing; a human --decision is the only thing that closes it).

the shared verification contract Nearly every agent step wraps deterministic tools and its check_*.py verifier. The runner never infers health from prose — it asserts each tool's own recorded verdict via health_requires:, so a polished file at full size still fails the step if the tool behind it fell back. Several verifiers double as index builders (--write-index / --write-report): the machine-readable seam a downstream step consumes is derived from the markdown, never hand-authored beside it, because two copies of the same findings drift and the drift always favours the summary.

§2 — Plan Extraction
2.1Plan Extractionagentopusskip if no attachments

Two independent readings of the same attached drawings, reconciled by a blind third pass that marks every disagreement as a data-gap rather than picking a winner. Reader A is a literal draftsman (geometry, dimension strings, callouts, tables, no interpretation); reader B reasons about what the features mean; neither ever sees the other. Independence is the whole mechanism — two readings from one context are one reading written twice, and a self-consistent misread is exactly what the double-read exists to catch. Records what the plan says only — no research, no compliance. Skips cleanly (records skipped:no-attachments) on an attachment-less run.

§3 — Research
3.1Pre-Gate Auditagentopus

The gate's own pre-flight: an adversarial read of every human-facing artifact the operator is about to be shown, against the run's own data. It runs three named attacks — prose-vs-own-data, disputed-as-settled, claim-with-no-artifact — and fixes confirmed defects through a recorded correction pass on the owning step before recording complete. This mechanizes the pilot's lesson: 1.2 and 2.1 each shipped an output that read cleanly and contradicted their own JSON, caught only because a Fable review was run by hand. Doing it by hand is not a mechanism. The auditor never runs run/verify itself.

§4 — Analysis & Synthesis
4.1Disciplines ×10agentopusrequires 3.4

The ten-agent discipline fan-out — one agent per canonical discipline, each reading its jurisdiction feasibility guide and applying it to the settled record. Before spawning, the author runs the geometry sidecar, writes premises.md (the confirmed frame, upstream corrections/supersessions, open postures no discipline may close by inference, and the routing table assigning each recorded conflict to its owning discipline), then cat-assembles each spawn brief on disk and spawns all ten in one message. Its own step because the ten files are distinct inputs to 4.2 and the failure class — one discipline dying quietly inside nine live ones — is the widest fan-out and the hardest thing to see in a polished report.
