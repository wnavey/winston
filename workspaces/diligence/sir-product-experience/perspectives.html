Perspective 01 — the product ownerJason's Vision: scale the workflow, keep the skill

"We're going to need to run four, five, ten of these a week. Right now we do one or two, and they're a lot of manual effort. I don't want to replace the skill or the human-in-the-loop steps — I want to build better interfaces around them."

The core ask, in one breath

Keep the interactive diligence-report Claude Code skill exactly as the engine (its flexibility is load-bearing). Attack the friction that lives at the interfaces — the hand-offs between people and tools — because that's what breaks at 10×. Two interface fronts, plus a delivery mechanism.

Front 1 — Client ↔ Noetic (intake + delivery)

Intake mostly exists

A chatbot-style intake: client drops PDFs, agent confirms it has a site definition (parcel/address), intended use, and any non-desk-research attachments (PUD, concept plan). Then it's queued. Staff (Heidi) can also do intake on a client's behalf.

Delivery UI high priority

Client logs in (or opens a secure link) and sees their reports with status. Web view of the report (infinite scroll, magazine-style site pages), download PDF/Word, and chat about the report.

Front 2 — Tech-lead ↔ Regulatory-specialist collaboration

Replace the Google-Doc/Slack/copy-paste loop with a DB-backed review surface on the main app. Assign a run to Sal or Garrett; they validate facts (HITL1) and review the draft (HITL3) with threaded comments + pasted screenshots; the tech lead threads replies; when locked, the agent reads the feedback straight from the database via MCP — no copy-paste.

Transitions are manual — the app gives visibility + notifications; humans pull the trigger. HITL2 (unblocking county-clerk CAPTCHAs, GIS debugging, paid pulls) stays entirely in Claude Code — no UI needed.

Delivery mechanism & where it lives

  • Secure obscurity URL is the default — no login required; link good for ~1–2 months; then require an account for history. Logged-in users see all their reports; chats are per-user scoped.
  • On the main app (app.noeticbuild.com), not Inspector General — this is a customer-facing commitment that must stay polished and up, unlike IG (the debugging tool).
  • Auto "your report is ready" email; default delivery is still Heidi/Jason emailing a link — but a Noetic link, not a Drive link.
Jason's own open question He was genuinely torn on whether the client interface or the specialist-collaboration interface is higher priority. Both are "big steps." (See Synthesis → Q3.)

Perspective 02 — the designerSal's Vision: the report as a map-centric, dual-audience web experience

Today the SIR ships as a 150–300 page PDF: linear, table-heavy, one audience at a time. Sal's prototype reimagines it as one screen where the map and the report are fused, the report is navigational instead of linear, and a single toggle flips the same view between the client report and the Noetic-internal evidence layer.

What this input is authoritative on Information architecture, the interaction model, the component system, and the feel. Not authoritative on scope, priority, or exact data-schema field names — it's a running prototype (vanilla JS + CDN), a spec to build against, not source to lift.

The load-bearing design bets

1 · The report is anchored by the site. The map isn't a widget beside the report — it is the left half, and every spatial finding lives on it. Biggest departure from the PDF.
2 · One view, two audiences, one toggle. Client ↔ internal adapts the same layout (reveals an evidence layer inline), never a second page. Mode is always visually obvious.
3 · The Finding Block is the atom. Dozens compose the whole report. Get it pixel-right and the rest falls into place. (anatomy below)
4 · Exec-summary-forward. 47 findings as full cards is unreadable → verdict + severity dashboard, then Top Risks full, then Moderate/Opportunity as one-line rows. Progressive disclosure.
5 · DATA GAP & "not applicable" are first-class. Clean intentional styling, never a red error look. A trust decision: report honestly what couldn't be verified.
6 · Native to the app. Steel-blue ramp, Lexend, Lora on report surfaces, the topographic-contour motif. Feels like it already lives in cityhall.

What Sal flags must change to make it real

CSP is the #1 landmine. Prototype's CDN scripts, Google fonts, and map tiles are all external hosts — blocked by cityhall's CSP. Must bundle locally + self-host/allowlist tiles.
Real GIS is the biggest fidelity gap. All prototype geometry is hand-authored placeholder. Needs real parcel/FEMA/wetlands/buildable/frontage/utility layers from the pipeline.
Real framework + data. Rebuild in SvelteKit/UnoCSS with real components; replace inline JS objects with pipeline output; formalize the schema as the API contract.
Client/internal = permissions. Gate the evidence layer behind Noetic-staff entitlement — never ship the Research Appendix in a client bundle by accident.

The two load-bearing decisions 1 · The app is a persistence + collaboration layer around an interactive Claude Code engine. Keep the skill (Jason's hard constraint); sync runs to the DB; the agent reads/writes review threads via MCP. Two existing skill-runners — interactive (has HITL, disk-only) and field-agent headless (has persistence, drops gates) — must be married.

2 · The findings-normalization layer is the pivot. Document-grade delivery needs none of it and ships first. Sal's map viewer needs it (plus real GIS) and ships later. Emit findings.json from the pipeline (write the same data already going into JSX).
