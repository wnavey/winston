Section 1 — the world as it existsToday: SIRs shoehorned onto submission

An SIR today is a submission row with submission_type='feasibility', existing only to anchor the intake URL. The intake conversation, the diligence run, and every artifact hang off a mix of project, that placeholder submission, the intake conversation, and the document that holds the captured facts. Below: the pertinent tables, then the two flows that exercise them.

1Flow — create the intake chat, state requirements, upload files

What gets written when a client (or staff on their behalf) starts an intake and drops PDFs.

1
cityhall bootstrap on project open
Creates a submission (type='feasibility') as a routing placeholder + a conversations row (type='intake', FK project_id). Also creates the sentinel document (kind='feasibility_intake', inline://feasibility-intake) + its document_version to hold the facts.
2
client types requirements → /api/chat/intake
Each turn persists a chat_message. The agent's updateIntakeNotes tool writes/updates document_section rows (Tier 1 site details / Tier 2 planned use / Tier 3 docs), source={kind:'chat'|'user_edit'}.
3
client drops a PDF → upload commits
prepare-upload → signed Storage PUT → commit-upload creates document (kind='intake_attachment') + document_version. On Send, a chat_message_attachment junction links the file to the message.
4
substation → Gemini extract → document_section
Inngest fan-out reads each PDF with Gemini, upserts document_section rows (skip-on-conflict by title), source={kind:'pdf_extract', document_version_id}. Realtime flips the RCM cards and refreshes the right panel.
Shoehorn #1 The submission type='feasibility' row does nothing but anchor the URL /project/[id]/submission/[submissionId]/intake/[conversationId]. None of its real children (submission_version, submission_plan_set) are ever created for an SIR.

2Flow — kick off the run, upload resources, surface in the UI

What happens from "Start research" through the deliverable appearing on the status page.

1
cityhall requestDiligenceRun → substation
POST /api/projects/:projectId/diligence with {document_version_id, conversation_id, full_run} + user JWT. Substation validates the doc_version belongs to the project and document.kind='feasibility_intake'.
2
INSERT diligence_runs (status=queued)
Anchored on document_version_id + conversation_id + project_id + triggered_by_user_id. Fires Inngest diligence/requested {diligence_run_id, full_run}.
3
field-agent runs the 6-phase skill
Consumes the event, marks running, invokes the diligence-report skill via the agent SDK. Produces the SIR + research appendix PDFs (+ supporting docs) on its local workdir.
4
upload → bucket submission-data
PDFs → diligence/<run-id>/. Then upsert diligence_artifacts on (diligence_run_id, kind) — kinds site_intelligence_report, research_appendix, supporting_document_copy. Run flips to completed.
5
UI status page renders View / Download
GET /api/projects/:projectId/diligence/:diligenceRunId returns the row + joined artifacts, each with a fresh 72-hour signed URL. Page: /project/[id]/diligence-runs/[runId]. This is where the SIR PDFs are surfaced today.
Storage today: bucket submission-data · path diligence/<run-id>/{site-intelligence-report,research-appendix}.pdf · signed URLs minted at read time (72h)
Shoehorn #2 — the two gaps (a) The authoritative subject location is resolved inside the run (Phase 0) but has nowhere to live on an entity — project.site_address is a vestigial hint (6/23 populated). (b) The interactive Claude Code runs (the real client SIRs) write only to local disk — only 11 diligence_runs have ever been persisted. Everything above is the headless field-agent path.

Section 2 — the same world, rebuiltThe Rework: a first-class site_intelligence_report entity

Per data-model.md (Draft v2): give the SIR its own entity carrying its own subject location, make project a neutral address-agnostic initiative container, and retire the submission type='feasibility' placeholder. Everything about the intake chat, documents, runs, artifacts and storage is unchanged — only the entity the conversation and run hang off of moves.

4

Section 3 — where the model goesThe Future: the SIR entity as the spine of the product

With the rework in place, the child specs (DESIGN-SPEC.md §12) hang net-new tables off the two anchors — site_intelligence_report and diligence_runs. The interactive Claude Code session and the web app become two clients of the same run record: the session writes artifacts + reads review threads via MCP; the app reads artifacts + writes review threads + delivers. Everything below is additive to Section 2.

How the three surfaces read the same object

Client surface
  • reads client-facing diligence_artifacts (PDF/Word/web HTML)
  • reads finding (P5) → map + dashboard (P6)
  • writes report_chat (P2)
  • entered via sir_share token or login
Staff collaboration + internal
  • reads/writes review_thread + review_comment (P3)
  • reads internal diligence_artifacts: manifest, mcp-calls, surveyor health (P4)
  • reads finding.provenance[] = the evidence layer
  • gated by is_noetic_admin / project_access
The synchronization point The interactive Claude Code session and the web app are two clients of the same Supabase run record. Session: writes artifacts + finding rows, reads locked review_threads via MCP. App: reads artifacts + findings, writes review threads, delivers via sir_share. The DB is the spine (DESIGN-SPEC §3.1).
