Section 2 — the near-term reworkThe Rework: human-kickoff local runs → site_intelligence_report + sir_artifact

Per data-model.md (Draft v3): in the near term an SIR is kicked off by a Noetic staffer on their laptop — they run the diligence-report skill in Claude Code, and on completion it publishes the deliverable to two new tables + storage, where it gets a home in the app. No intake chat, no Inngest, no field-agent, no diligence_runs. The run's only DB footprint is the completion-time publish.

what section 1 had that this removes The entire app-intake + field-agent path is gone from the near-term SIR flow: the submission type='feasibility' placeholder, the intake conversations / chat_message / document_section capture, the requestDiligenceRun tool + Inngest event, the field-agent laptop worker, and the diligence_runs run-tracking table. Today's scenes 2–5 collapse away entirely; scenes 1, 6, 7 become the four scenes below.

What the rework does — at a glance

Removed from the SIR path
  • submission type='feasibility' placeholder
  • Intake chat: conversations / chat_message / document_section + Gemini extraction
  • requestDiligenceRun tool + Inngest event
  • field-agent laptop worker
  • diligence_runs run-tracking table (fails 1:1 reuse — D2)
New / net structure
  • NEW site_intelligence_report (subject location + current_version)
  • NEW sir_artifact (flat-versioned files: version + versioning_label, kind×format)
  • Local run → service-role publish on completion
  • App SIR list + detail (version switcher for staff)
  • RLS clones + realtime on both tables
Deferred (not near-term) — the intake-chat / self-serve-prospect path; the holding-org / prospect→customer re-home (was v2 §3.6, now Future G1); a sir_version table + compare/lineage UI (promote from the flat model when a 2nd per-version attribute appears — D11); a coarse status field (add when the internal dashboard F1 needs it — D4).

Section 3 — where the model goesThe Future: net-new use cases to model

Section 2 delivers the structural spine (the site_intelligence_report entity + the diligence_runs FK). The rest of the SIR product layers on many more capabilities, each needing its own data-model support. This tab is the scoped catalog of those use cases — the input list for a dedicated per-use-case modeling session and the child specs in DESIGN-SPEC.md §12. It is intentionally not modeled here: the ★★ items are hard enough to warrant their own specs.

#n from the original brief + surfaced from the specs ★ net-new / hard modeling ★★ likely its own spec dimmed = deferred / gated
A Intake & kickoff
A1#1Self-serve intake chat — client states requirements, uploads files, and kicks off the run.
A2+Staff-initiated intake on a client's behalf ("create for org X").
B Run execution & persistence
B1#1★Run executes to the first HITL gate, publishes DB row(s), and fires a "ready for review" notification.
B2#3★Run emits phase / progress data to the DB at intervals (defined phase entities) — also the substrate for resume (B6).
B3#4On complete: publish structured entity data + PDF + Word + web-HTML + ancillary contents + metadata to DB + storage.
B4#5On complete: fire a completion notification to a channel (Slack / email / in-app — generic).
B5+Stuck-run reconciler + retry (orphaned running → failed/queued; retry a failed extraction).
B6#7★★Resume a partial / failed run — every phase (new pipeline + old skill) emits phase-completion + ancillary context so a fresh session reloads and continues from the last good phase.
C Versioning & modification
C1#7★★Request changes via Claude → a new internal version of the artifact set for human review & compare. Internal convention only — there is exactly one customer-facing SIR; versioning is invisible to the client.
D Staff review collaboration
D1+Tech lead assigns a run to a regulatory specialist.
D2+★Specialist leaves threaded review comments (text + links + pasted images) on the HITL1 facts; drafts accumulate until submit.
D3+Tech lead threads replies and locks (or kicks back); specialist can flag "re-review me".
D4+The Claude agent reads locked feedback via MCP — no copy-paste.
D5+HITL3 report-draft review — same threaded pattern over the finished draft.
D6+HITL2 deep-research unblocking stays in Claude Code; the app only reflects state (no interaction surface).
E Delivery & client
E1#6Reviewer approves final → "send" in the UI → generate file links + send email (email send may be manual).
E2+Secure obscurity-URL delivery — no-login time-limited link (~1–2 mo), then account-required for history.
E3+Client web viewer — infinite-scroll HTML rendering + PDF / Word download.
E4+Report chat — Q&A over report contents, per-user-scoped history.
F Internal views & observability
F1#2Internal user views all SIRs, filterable by status (queued / active / completed / failed / …).
F2+Under-the-covers observability — run telemetry, which MCP tools ran, surveyor health, cost, data gaps.
G Access & tenancy
G1+★Prospect → customer conversion — re-home project.owner_organization_id off the holding org; sweep stray project_access grants.
G2+Entitlement layering — client vs staff vs internal enforced as a permission, never a UI toggle.
H Findings & rich viewer (later, gated)
H1+★Pipeline emits normalized findings.json → finding records — the pivot that unlocks the map viewer and the internal evidence layer.
H2+Rich map-anchored viewer with per-finding cards + dual-audience toggle (gated on H1 + real GIS).
H3+field-agent HITL convergence — the runner pauses at gates; the app becomes the HITL surface.
the two heavy hitters B6 (resume a partial run) and C1 (internal SIR versioning) are the ★★ items. Each needs dedicated design — phase-completion emission across the new pipeline and the old skill for resume; an internal version model behind a single customer-facing SIR for versioning — and each likely becomes its own child spec.
